Research date: 2026-10-29. Note on provenance: three background sub-researcher agents were
originally dispatched to cover (a) Pipecat/LiveKit/TEN/Vocode, (b) KoljaB tools/Speaches/Wyoming,

## Which framework is the best fit for: fully local voice components + custom agent-harness LLM step + low latency + running on M1 Mac or RTX 3070 Linux box?

### Takeaway
**Pipecat** is the best fit: it has first-party, documented local-only examples for exactly this shape (SmallWebRTC + Silero VAD + local Whisper + local LLM + local TTS, including an M-series Mac walkthrough), a clean `LLMService`/`FrameProcessor` abstraction that is not tied to OpenAI's wire format, and is the most actively maintained/corporately-backed project in the set. **LiveKit Agents** is the strongest runner-up — more mature interruption/turn-detection and async-tool machinery — but self-hosting LiveKit server adds an extra moving part. **KoljaB's RealtimeSTT/RealtimeTTS** are good as local STT/TTS *components* (used as libraries, not full orchestrators) but the `RealtimeVoiceChat` reference app that glues them together is explicitly unmaintained. Vocode is essentially dead and not recommended for new work.

### Cited Findings
- Pipecat is "Open Source framework for voice agents, multimodal apps, and realtime AI. Maintained by Daily and the community," with ~16.9k GitHub stars / ~3.0k forks — [GitHub](https://github.com/pipecat-ai/pipecat); star count corroborated at ~16.4k–16.9k across sources as of Oct 2026 — [star-history](https://www.star-history.com/pipecat-ai/pipecat), [Forasoft comparison](https://www.forasoft.com/blog/article/pipecat-vs-livekit-agents).
- Pipecat ships a dedicated macOS example repo, `kwindla/macos-local-voice-agents`: "Pipecat voice AI agents running locally on macOS," claiming voice-to-voice latency under 800 ms on M-series Macs using the `SmallWebRTCTransport` for a local, serverless peer-to-peer connection — [GitHub](https://github.com/kwindla/macos-local-voice-agents), [Pipecat SmallWebRTC docs](https://docs.pipecat.ai/client/js/transports/small-webrtc).
- A community example documents a fully CPU-only local cascade: `SmallWebRTC → Silero VAD → Whisper (tiny/base, CPU int8) → Ollama LLM → Kokoro TTS` — [pipecat/examples/README](https://github.com/pipecat-ai/pipecat/blob/main/examples/README.md).
- Another community repo, `mthomas100/local-voice`, describes "a fully local voice agent for Apple silicon: Pipecat, streaming ASR, Qwen3-TTS, a local LLM via Pi, with iPhone and Mac apps (~0.87s to first audio)" — [GitHub](https://github.com/mthomas100/local-voice).
- Pipecat's LLM integration point is `pipecat.services.llm_service` — subclasses implement `run_inference()` for one-shot, out-of-pipeline inference, and custom `FrameProcessor`s can wrap/replace the LLM node inside a `Pipeline`; docs explicitly cover "Custom FrameProcessor" and "Multiple LLM Agents" patterns — [llm_service docs](https://reference-server.pipecat.ai/en/stable/api/pipecat.services.llm_service.html), [Custom FrameProcessor](https://docs.pipecat.ai/pipecat/fundamentals/custom-frame-processor), [Multiple LLM Agents](https://docs.pipecat.ai/pipecat/learn/multiple-llm-agents).
- LiveKit Agents (`livekit/agents`) has ~14.2k–14.6k GitHub stars, Apache-2.0 license (turn-detection *models* under a separate LiveKit Model License) — [star-history](https://www.star-history.com/livekit/agents/), [LICENSE](https://github.com/livekit/agents/blob/main/LICENSE).
- LiveKit's LLM plugin interface: plugins subclass `LLM` and implement `chat()` returning an `LLMStream`; for deeper control, LiveKit docs describe customizing the `llm_node` directly to call an arbitrary provider, not just OpenAI-compatible HTTP — [Custom LLM Providers KB article](https://kb.livekit.io/articles/3629410652-using-custom-llm-providers-with-the-agent), [LLM Integration deepwiki](https://deepwiki.com/livekit/agents/4-llm-integration). LiveKit also has an official blog post on bridging LangChain agents into LiveKit, suggesting arbitrary custom agent frameworks are a supported pattern, not just single LLM calls — [LiveKit blog: Bring your LangChain agents to LiveKit](https://livekit.com/blog/langchain-to-livekit).
- LiveKit requires self-hosting (or using cloud) a separate LiveKit **server** (SFU) in addition to the `agents` Python/Node worker process, which is an extra deployment component versus Pipecat's `SmallWebRTCTransport`, which needs no separate media server for local/dev use — [Pipecat SmallWebRTC server docs](https://docs.pipecat.ai/api-reference/server/services/transport/small-webrtc) vs. general LiveKit self-host architecture knowledge (LiveKit server + agents worker + SIP/room). *(This is an inference from each project's documented architecture, not a single direct citation — see Inferences.)*
- RealtimeSTT has ~10.1k–10.2k GitHub stars, MIT license; RealtimeTTS has ~4.0k stars, MIT license — [RealtimeSTT star-history](https://www.star-history.com/koljab/realtimestt/), [RealtimeTTS repo](https://github.com/KoljaB/RealtimeTTS), [RealtimeSTT repo](https://github.com/KoljaB/RealtimeSTT).
- `RealtimeVoiceChat` (the KoljaB reference app that wires RealtimeSTT + RealtimeTTS + an LLM together over WebSockets) is "no longer being actively maintained by KoljaB due to time constraints, and he will no longer be implementing new features or providing user support" — [GitHub](https://github.com/KoljaB/RealtimeVoiceChat) (per search-engine-summarized repo README/notice).
- Vocode: the core OSS repo (`vocodedev/vocode-core`, MIT) "last commit... dates from November 2024 and the last stable release from June 2024, the vocode.dev domain now redirects to the GitHub organisation, and Y Combinator lists the company as acquired... The repository is neither archived nor marked deprecated, so it still appears healthy in search results" — [search synthesis citing vocodedev/vocode-core releases/issues](https://github.com/vocodedev/vocode-core/releases).
- TEN Framework (`TEN-framework/ten-framework`) is Apache-2.0 "with additional restrictions," supports extensions in C++/Go/Python/JS/TS, and has a companion `ten-vad` model on Hugging Face plus its own turn-detection component; as of November 2025 TEN Framework "celebrates one year anniversary as open source infrastructure for real time conversational ai development" (Reuters wire item) — [GitHub](https://github.com/TEN-framework/ten-framework), [ten-vad on HF](https://huggingface.co/TEN-framework/ten-vad), [Reuters/TradingView item](https://de.tradingview.com/news/reuters.com,2025-11-02:newsml_NFC6ZfHY7:0-ten-framework-celebrates-one-year-anniversary-as-open-source-infrastructure-for-real-time-conversational-ai-development).

### Inferences
- Pipecat's architecture (process graph of `FrameProcessor`s connected in a `Pipeline`, with `LLMService` as just one processor type) is inherently more "bring your own black-box step" friendly than a chat-completions-shaped plugin interface, because frames (text, audio, control) flow through arbitrary processors — swapping in a call to Claude Agent SDK or an OpenCode server is a matter of writing one processor, not satisfying a provider-shaped interface.
- For an RTX 3070 Linux box specifically, nothing found above is GPU-vendor-specific — Pipecat, LiveKit Agents, and the KoljaB libraries all work via standard PyTorch/CUDA-backed local STT (faster-whisper/whisper.cpp) and TTS (Kokoro, XTTS, Piper) stacks, so the choice is driven more by orchestration-layer fit than by GPU support.
- Running LiveKit's turn-detector/VAD stack fully locally is supported, but LiveKit's newer default "adaptive" interruption mode uses an audio classifier model (see next section) which is an additional local model dependency beyond plain VAD — worth budgeting for on the M1/RTX3070 boxes.

### Gaps
- No direct repo-level comparison found for raw end-to-end latency numbers (Pipecat vs LiveKit Agents vs TEN) on identical M1/RTX3070 hardware; cited latency figures (e.g. "<800ms," "~0.87s to first audio," "~500ms" for RealtimeVoiceChat) come from different example repos with different model/hardware choices and are not apples-to-apples.
- Did not independently verify TEN Framework's current GitHub star count or most recent release/commit date (search results returned marketing/anniversary coverage rather than a live stars/commits figure); flag as unverified for freshness.
- Did not get independent confirmation of LiveKit Agents' or Pipecat's current contributor counts or Discord sizes (community health depth is thin here — see below).

## How does each handle a slow LLM/agent (long tool-using turns): can you inject filler/status speech, run async background tasks, and speak proactive notifications?

### Takeaway
LiveKit Agents has the most explicitly documented, first-class support for this: `session.say()` for filler bypassing the LLM, native async/background tool execution, a `ctx.foreground()` primitive for a background task to interject mid-run, and a configurable template for turning background-tool status updates into spoken notifications. Pipecat supports the same pattern (tool-call filler messages) but as a requested/emerging feature rather than a fully polished built-in — there's an open GitHub issue specifically asking for first-class "tool call filler/acknowledgement" support, implying teams currently hand-roll it.

### Cited Findings
- LiveKit: `session.say()` triggers TTS playback and returns a `SpeechHandle` to track state — can be called at any time, including from a background task — [Agent speech docs](https://docs.livekit.io/agents/build/speech/).
- LiveKit: "Tools can run synchronously or in the background, letting the agent keep talking while long-running work completes." `RunContext` provides filler speech via `session.say()` "bypassing the LLM... for filler like 'hang on a sec' or 'still working on it' during work the LLM doesn't need to track." A `ctx.foreground()` block lets a background tool interject mid-run: it "first plays any reply the tool has already queued, waits for the session to be idle, then prevents other agent speech for the duration of the block." There's also a configurable "update template" for background-tool status announcements, e.g. "Background tool `{function_name}` reports: {message}. Acknowledge briefly." — [Async tools docs](https://docs.livekit.io/agents/logic/tools/async/), [LiveKit blog: Async tools for voice agents](https://livekit.com/blog/async-tools-voice-agents).
- LiveKit community threads show this is an active area of iteration/debate ("We need to talk about pre-tool-call speech," "How to enforce agent tool call pre-speech"), indicating the feature is real but still being refined by users in practice — [community thread 1](https://community.livekit.io/t/we-need-to-talk-about-pre-tool-call-speech/1152), [community thread 2](https://community.livekit.io/t/how-to-enforce-agent-tool-call-pre-speech/448).
- Pipecat: an open GitHub issue, "Add support for Tool call Fillers/Acknowledgement messages" (#4492), frames the gap directly: "When invoking tool calls, it increases the latency since it involves an extra LLM turn involving the tool, that the user is not easily made aware of." The proposed/documented pattern is "for each tool a specific filler message can be defined that will be spoken by the agent as soon as the LLM generates the text that will trigger the tool call," sized to mask the tool's expected duration — [GitHub issue #4492](https://github.com/pipecat-ai/pipecat/issues/4492).
- Broader research context: a 2026 arXiv benchmark (Full-Duplex-Bench-v3) on tool use under real-world disfluency notes some models show "an inverted latency profile where... tool-call latency is the slowest—the model speaks before it calls any tool" with an "88.0% filler rate," but also warns "filler speech frequently overlaps with the user's utterance and deferring tool execution until after the filler inflates task-completion latency" — i.e., filler-speech-during-tool-calls is a known hard UX problem industry-wide, not fully solved by any framework — [arXiv paper](https://arxiv.org/pdf/2604.04847).

### Inferences
- Because Pipecat is just a frame-processing pipeline, "proactive/background speech" is achievable by having any processor push a TTS-bound text frame asynchronously (e.g. from a background asyncio task) — the capability is architecturally present even where it isn't yet a named, polished feature as it is in LiveKit.
- For a custom agent harness with genuinely long tool-using turns (multi-second Claude Agent SDK tool loops), LiveKit's `ctx.foreground()` / background-tool-update-template pattern is closer to "out of the box" than anything found for Pipecat, TEN, or the KoljaB tools, which generally expect you to hand-wire this behavior yourself at the processor/callback level.

### Gaps
- No equivalent first-class "filler/background notification" documentation found for TEN Framework, Vocode, or the KoljaB tools — likely because these either don't document the pattern or it simply isn't a built-in (TEN's docs weren't explored at this depth; Vocode is unmaintained; KoljaB tools are lower-level libraries without turn/session orchestration concepts at all).
- Did not verify whether Pipecat has since shipped a built-in filler-message API after issue #4492 was opened — the issue's current status (open/closed, and whether a PR landed) was not checked.

## What client options exist (browser WebRTC, native desktop, phone/SIP telephony) for a "call your agent" experience?

### Takeaway
LiveKit has the broadest built-in multi-client story (browser WebRTC SDKs, native mobile/desktop SDKs, and SIP/telephony bridging as part of its core server), because it's fundamentally a WebRTC media-server platform with agents layered on top. Pipecat supports browser WebRTC (SmallWebRTC and its own client-web-transports repo) and has telephony integration patterns via its transport abstraction, but SIP/phone support is less central to its identity than LiveKit's. Vocode was originally built explicitly around phone calls (Twilio/Zoom) but is now unmaintained, so that use case is best served elsewhere today.

### Cited Findings
- Pipecat has a dedicated mono-repo, `pipecat-ai/pipecat-client-web-transports`, "to house the various supported Transport options to be used with Pipecat's client-js package," and official guidance on "Choosing a Transport" — [GitHub](https://github.com/pipecat-ai/pipecat-client-web-transports), [Choosing a Transport docs](https://docs.pipecat.ai/client/concepts/choosing-a-transport).
- Vocode's original pitch: "build real-time, streaming voice AI agents that run over phone calls" with a hosted REST API at `api.vocode.dev/v1` for placing/managing outbound and inbound phone calls, plus support for joining Zoom meetings — [vocode-core README summary](https://github.com/vocodedev/vocode-core/blob/main/README.md), [third-party Vocode profile](https://github.com/api-evangelist/vocode).
- LiveKit Agents' docs and KB describe a plugin-based architecture unifying VAD/STT/LLM/TTS across 15+ providers and reference first-class SIP integration as part of the LiveKit platform (general LiveKit platform knowledge; telephony/SIP is a standard LiveKit server feature) — [LLM Integration deepwiki](https://deepwiki.com/livekit/agents/4-llm-integration) (SIP specifics not independently re-verified this pass — see Gaps).
- TEN Framework markets itself as supporting multimodal real-time interaction with a web demo agent at `agent.theten.ai` and multi-language extensions (C++/Go/Python/JS/TS), implying broad client/platform reach, though specific SIP/telephony support was not directly confirmed — [GitHub](https://github.com/TEN-framework/ten-framework).

### Inferences
- For a "phone call into your agent" product specifically, LiveKit (with its SIP trunking support as part of the core platform) is likely the most turnkey of the actively-maintained options; Pipecat can get there via its transport abstraction but telephony is one of several transport options rather than the platform's center of gravity.

### Gaps
- Did not directly fetch LiveKit's SIP/telephony docs this pass to confirm self-hosted (non-cloud) SIP trunking works identically to the hosted offering — flagged as needing direct doc verification.
- Did not find primary-source confirmation of TEN Framework's SIP/telephony support specifically.
- Did not check whether Pipecat's SmallWebRTC or other transports support native desktop (non-browser) clients beyond the generic client-js/web-transports story — native desktop/mobile SDK maturity for Pipecat vs. LiveKit was not directly compared with citations.

## Speech-to-speech / full-duplex models (Moshi, Sesame CSM, Ultravox, Qwen-Omni, etc.): are they practical here given the LLM must be an external agent harness?

### Takeaway
These models mostly **conflict** with the "bring your own external agent harness" requirement, because their whole value proposition is collapsing STT+reasoning+TTS into one model/latency budget — there is no clean seam to swap in a multi-second, tool-calling agent process. The one notable exception is **Kyutai Unmute**, which is explicitly architected the opposite way: local STT/TTS + semantic turn detection wrapped around *any* separate text LLM, which is structurally the closest fit to the project's requirement among all speech-centric (non-orchestrator-framework) options found.

### Cited Findings
- **Kyutai Moshi**: "a 7B-parameter speech-to-speech foundation model... Moshi generates speech as tokens from the residual quantizer of a neural audio codec, while modeling separately its own speech and that of the user into parallel streams... full-duplex capability — it listens and speaks simultaneously... theoretical latency of 160ms, 200ms in practice" — [GitHub](https://github.com/kyutai-labs/moshi), [arXiv paper](https://arxiv.org/abs/2410.00037). This is a single monolithic model with reasoning baked in; there is no separate "LLM step" to swap.
- **Kyutai Unmute** (distinct from Moshi): "Make text LLMs listen and speak... wrapping them in Kyutai's Text-to-speech and Speech-to-text models. The speech-to-text transcribes what the user says, the LLM generates a response in text, and the text-to-speech reads it out loud... the system works with any text LLM you like." It provides "streaming speech-to-text, semantic voice activity detection that predicts whether the user has actually finished speaking, and streaming text-to-speech that can begin before the LLM has finished generating." Default local config uses `google/gemma-3-1b-it`; by default Unmute uses Mistral Small 3.2 24B — [GitHub](https://github.com/kyutai-labs/unmute).
- **Ultravox** (fixie-ai): "a new kind of multimodal LLM that can understand text as well as human speech, without the need for a separate Audio Speech Recognition (ASR) stage... extends any open-weight LLM with a multimodal projector that converts audio directly into the high-dimensional space used by LLM." Built on Llama 3.3 70B by default, with Mistral/Gemma variants; latest noted version "Ultravox 0.7" as of December 2025 — [GitHub](https://github.com/fixie-ai/ultravox), [search summary of releases](https://github.com/fixie-ai/ultravox/releases). Ultravox is speech-*in*, text-*out* (it replaces the STT+LLM fusion, not the full duplex audio-out side) — note this is an audio-understanding-fused-LLM, not a full speech-to-speech model; a separate TTS step is still needed downstream, but the "LLM reasoning" and "STT" steps are fused into one model/weights, so you cannot cleanly insert an external agent harness without essentially replacing Ultravox's core function.
- **Sesame CSM**: "generates RVQ audio codes from text and audio inputs... employs a Llama backbone and a smaller audio decoder that produces Mimi audio codes," 1B variant released 2025/03/13, community forks add MLX (Apple Silicon) support — [GitHub](https://github.com/SesameAILabs/csm), [community MLX fork](https://github.com/akashjss/sesame-csm). CSM is fundamentally a conversational TTS/speech-generation model (text+audio context → speech), not a full reasoning engine — it could plausibly serve as the *TTS* component in a bring-your-own-agent pipeline, but it is not itself a speech-to-speech reasoning model competing with Unmute/Moshi.
- **Hugging Face `speech-to-speech`**: "an effort for an open-sourced and modular GPT4-o," implementing "a speech-to-speech cascaded pipeline consisting of Voice Activity Detection (VAD), Speech to Text (STT), Language Model (LM), and Text to Speech (TTS)... fully open and modular," ~4.3k stars / 487 forks — [GitHub](https://github.com/huggingface/speech-to-speech), [KDnuggets writeup](https://www.kdnuggets.com/striving-open-source-modular-gpt4o-hugging-face-speech). Because it's explicitly a *cascaded, modular* pipeline (not a fused end-to-end model), its "LM" stage is architecturally a separate, swappable component — structurally similar in spirit to Pipecat/Unmute rather than to Moshi/Ultravox/CSM.
- **Qwen2.5-Omni / Qwen3-Omni**: "end-to-end multimodal model by Qwen team at Alibaba Cloud, capable of understanding text, audio, vision, video, and performing real-time speech generation" with "real-time streaming responses through both text generation and natural speech synthesis"; Qwen3-Omni adds "Speech-to-Text / Speech-to-Speech translation" — [Qwen2.5-Omni GitHub](https://github.com/QwenLM/Qwen2.5-Omni), [Qwen3-Omni GitHub](https://github.com/QwenLM/Qwen3-Omni), [Qwen blog](https://qwenlm.github.io/blog/qwen2.5-omni/). These are single end-to-end weights fusing understanding+generation, same category as Moshi/Ultravox.

### Inferences (clearly labeled as reasoning, not sourced fact)
- True end-to-end speech-to-speech models (Moshi, Ultravox, Sesame CSM, Qwen-Omni) are poor fits for the stated requirement: their low-latency value proposition depends on reasoning happening *inside* the same forward pass/model that handles audio, so routing to an external multi-second, tool-calling agent process (Claude Agent SDK / OpenCode server) either breaks their latency model entirely or requires discarding most of what makes them distinctive (you'd just be using them as a fancy ASR, throwing away their native generation).
- Kyutai Unmute and the Hugging Face `speech-to-speech` project are the two best candidates in this category for "bring your own agent harness," because both are explicitly cascaded (separate STT/VAD → text → separate TTS) rather than fused, and both are documented as accepting "any text LLM" — in principle, the "text LLM" slot in either could be replaced by a bridge/adapter process that forwards the transcript to Claude Agent SDK or an OpenCode server and streams back the final text for TTS. This would need an adapter layer (an HTTP/OpenAI-compatible shim or an in-process callable) and has not been verified against either project's actual code interface in this pass.
- Sesame CSM is more realistically evaluated as a *candidate local TTS engine* to plug into Pipecat/LiveKit/Unmute than as a competing full pipeline.

### Gaps
- Did not confirm from Unmute's actual source code whether the "any text LLM" integration point is literally an OpenAI-compatible HTTP call (which would make swapping in a custom agent harness as easy as pointing `base_url` at a shim) or something more bespoke/tightly coupled to its streaming/turn-taking logic — this is an important open question for feasibility and should be checked directly in `kyutai-labs/unmute`'s docker-compose/config and backend source before relying on it.
- Did not verify hardware/VRAM requirements for self-hosting Moshi, Unmute, Ultravox, Sesame CSM, or Qwen-Omni on an RTX 3070 (8GB) specifically — these models range from 1B to 70B+ parameters and VRAM feasibility on a 3070 is very likely a hard constraint for several of them (not confirmed with sources this pass).
- GPT-4o Realtime API and other closed speech-to-speech systems were intentionally excluded as non-OSS per the task scope.
