# Latency Budgets and Bridging a Slow Agent Harness into a Real-Time Voice Loop

## What is the accepted voice-to-voice latency target, and how is the budget split?

### Takeaway
Industry consensus puts "feels natural" voice AI latency at roughly 300-500ms end-to-end (voice-to-voice), with sub-600ms considered acceptable and >600-800ms starting to feel noticeably laggy; the human conversational turn-taking gap is a much tighter ~200ms. A representative p50 budget split across a cascaded pipeline is roughly: endpointing/VAD ~80ms, ASR finalization ~120ms, LLM time-to-first-token ~180ms, TTS time-to-first-audio ~70ms (≈450ms total), with network/transport added on top.

### Cited Findings
- LiveKit Agents targets a sub-500ms latency budget as "the critical threshold separating useful from unusable voice agents"; under 300ms feels human, 300-600ms feels sluggish but acceptable, above 600ms callers mentally revert to touch-tone/IVR expectations — [Forasoft LiveKit AI Voice Agents 2026 Playbook](https://www.forasoft.com/blog/article/livekit-ai-agents-guide)
- A representative sub-500ms latency budget: endpointing 80ms + ASR 120ms + LLM 180ms + TTS 70ms ≈ 450ms p50 — [Evalgent, LiveKit vs Pipecat Latency: Where the Time Goes](https://www.evalgent.com/blog/livekit-vs-pipecat-latency)
- Pipecat's sequential pipeline (transport → STT → LLM → TTS) typically runs 500-800ms round trip under standard conditions; with matched STT/LLM/TTS stacks, LiveKit and Pipecat land within ~50-100ms of each other — [Evalgent, LiveKit vs Pipecat Latency](https://www.evalgent.com/blog/livekit-vs-pipecat-latency)
- Kyutai's Unmute (cascaded STT→text-LLM→TTS wrapper, not a native audio-to-audio model) delivers ~450ms response time in production, with conversational latency typically 400-750ms; Unmute's STT includes a "semantic VAD" that predicts whether the user has actually finished speaking (vs. mid-sentence pause) to avoid premature/false turn-taking while still being low-latency; the TTS begins generating audio before the LLM's text response is complete, to shave the end-to-end number — [Unmute docs / Kyutai](https://www.mintlify.com/kyutai-labs/unmute/introduction); [Kyutai on X re: semantic VAD](https://x.com/kyutai_labs/status/1925840425052426634)
- For contrast, fully audio-native end-to-end models claim ~160-200ms end-to-end latency but "struggle with tasks like complex tool calling or specific structured formatting" — [Towards AI, Unmute deep dive](https://pub.towardsai.net/unmute-giving-voice-to-ai-a-deep-dive-into-kyutais-framework-6d8f83bc9531)
- Human conversational turn-taking gap: a widely-cited empirical study (Stivers et al.) across 10 languages found the average turn-taking gap is ~208ms — [dev.to summary of ACL IWSDS 2025 discussion of Stivers](https://dev.to/kenimo49/200ms-humans-vs-700ms-voice-agents-what-acl-iwsds-2025-says-about-the-turn-taking-gap-2iap)
- Industry benchmarks put median voice-AI response time at 1,400-1,700ms as of the cited analysis — roughly 5-8x slower than the ~200ms human benchmark, explaining why many voice agents still feel unnatural even when individually "fast" — [dev.to, 200ms Humans vs 700ms Voice Agents](https://dev.to/kenimo49/200ms-humans-vs-700ms-voice-agents-what-acl-iwsds-2025-says-about-the-turn-taking-gap-2iap)
- A separate finding on turn-taking mechanics: short turn-transition gaps (100-300ms) occur even though language-production latency is 600-1500ms, implying humans begin preparing their next utterance before the other party finishes speaking (predictive turn-taking) — [dev.to, same article, citing turn-taking literature](https://dev.to/kenimo49/200ms-humans-vs-700ms-voice-agents-what-acl-iwsds-2025-says-about-the-turn-taking-gap-2iap)

### Inferences
- A cascaded local-STT + agent-harness-LLM + local-TTS pipeline realistically lands in the 450ms-1500ms range depending heavily on which piece dominates (the agent harness, not STT/TTS, is almost certainly the bottleneck — see next section). Hitting the "feels human" ~200-300ms gap is not achievable with any LLM-in-the-loop architecture, agent harness or not; the practical target to aim for is the ~450-800ms "acceptable, not sluggish" band that Pipecat/LiveKit/Unmute production systems cluster around.
- Because an agent harness (multi-turn tool use, file reads, subagent dispatch) is fundamentally slower than a single LLM completion, bridging it into a sub-800ms voice loop requires architectural decoupling (see dual-model section) rather than trying to make the harness itself faster.

### Gaps
- No primary academic citation (e.g., the original Stivers 2009 PNAS paper) was directly fetched — only secondary summaries citing it were found in the time available; the report writer should treat the "~208ms" figure as well-corroborated but secondhand-sourced here.

## Time-to-first-token: Claude Agent SDK / Claude Code headless vs. direct API vs. OpenCode server vs. ACP — which gives lowest TTFT and best interruption support?

### Takeaway
Direct Anthropic API streaming (with prompt caching) gives the lowest and most predictable TTFT; Claude Agent SDK / headless `claude -p` adds meaningful process-startup and discovery overhead on top of the same underlying API call, and has documented streaming reliability issues. OpenCode's server exposes an SSE event stream that forwards incremental message parts similarly to the SDK's partial-message mode. ACP standardizes streaming (`session/update`) and cancellation (`session/cancel`) at the protocol level but explicitly does not guarantee any latency/time-to-first-update bound — it only guarantees ordering/semantics, not speed. All three support cancel/interrupt, but ACP's spec is the most formally rigorous about what must happen (and in what order) around a cancel.

### Cited Findings
- **Claude Agent SDK**: Enabling `include_partial_messages`/`includePartialMessages` yields raw `StreamEvent`s (`content_block_delta`, etc.) as they arrive, in addition to complete `AssistantMessage`/`ResultMessage` objects — this is the mechanism for low TTFT perception in a custom UI — [Claude Code Docs, Stream responses in real-time](https://code.claude.com/docs/en/agent-sdk/streaming-output)
- Known reliability issue: with `ClaudeSDKClient` (Python, streaming-input mode), `StreamEvent` objects are "either never yielded or yielded unreliably" — [GitHub anthropics/claude-code#17956](https://github.com/anthropics/claude-code/issues/17956)
- On Bedrock, SDK 0.3.x was found to buffer the entire model response and emit all `stream_event` text deltas at the very end of the call (vs. 0.2.34 which streamed incrementally), i.e. a regression that defeats TTFT entirely for that backend — [GitHub anthropics/claude-agent-sdk-typescript#511](https://github.com/anthropics/claude-agent-sdk-typescript/issues/511)
- Stream events carry raw deltas only for the *main* session; "token-level deltas from subagents aren't forwarded" — only complete messages (with `parent_tool_use_id`) surface subagent output, so a dispatched subagent's work is invisible at token granularity until it completes — [Claude Code Docs, Stream responses in real-time](https://code.claude.com/docs/en/agent-sdk/streaming-output)
- Cancellation/interruption: the docs describe an "interrupted turn" as one valid cause of a cut-off stream, and specify that `message_stop` always arrives even on interruption, though `content_block_stop`/`message_delta` may be skipped — i.e., the SDK supports interrupt-and-resume but callers must handle partial/incomplete tool-call JSON — [Claude Code Docs, Stream responses in real-time](https://code.claude.com/docs/en/agent-sdk/streaming-output)
- Headless `claude -p` startup overhead: by default it performs auto-discovery of hooks, skills, custom commands, subagents, plugins, MCP servers, memory, and CLAUDE.md on every invocation; a `--bare` flag skips this for CI/scripting use — implying non-bare headless invocations pay a fixed discovery cost before the first token — [swareco.com, Claude Code Headless Mode](https://www.swareco.com/blog/claude-code-headless-mode) (flag described also per Claude Code docs ecosystem)
- A tracked regression: median time-to-first-stdout for headless/schema-bound `claude -p` increased from 1553ms (v2.1.197) to 2295ms (v2.1.222) on Linux arm64 — roughly a 700ms regression attributable to the harness/CLI layer itself, not the model — [GitHub anthropics/claude-code#87652](https://github.com/anthropics/claude-code/issues/87652)
- A separate issue reports headless `claude -p` (`sdk-cli` entrypoint) consuming ~1.8x more of the time-boxed usage window per token than interactive `cli` mode for the same workload, suggesting non-trivial harness overhead beyond pure model latency — [GitHub anthropics/claude-code#97074](https://github.com/anthropics/claude-code/issues/97074)
- `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` lets a caller cap how long headless mode waits for MCP servers to connect before proceeding with the first turn — directly relevant to shaving startup latency for a voice-triggered headless invocation — [juliangoldieaiautomation.com, Claude Code MCP Server Startup Timeout](https://juliangoldieaiautomation.com/blog/claude-code-mcp-server-startup-timeout/)
- **Direct API / prompt caching**: Anthropic states prompt caching can reduce latency "by up to 85% for long prompts"; a documented pre-warming technique sends the system prompt with output disabled so it's cached before the real user turn arrives, eliminating the cache-miss penalty on the latency-critical first turn — [Anthropic, Prompt caching](https://www.anthropic.com/news/prompt-caching); [X/Mikel Echeverria summarizing Anthropic's pre-warming trick](https://x.com/MikelEcheve/status/2055071920614146556)
- One developer reported a 79% TTFT reduction chatting against a 100,000-token cached prompt — [signoz.io, How to Reduce Claude API Latency](https://signoz.io/guides/claude-api-latency/)
- Claude Haiku 4.5 (non-reasoning) delivered first token in 597ms on a medium-length prompt in one benchmark — a reasonable floor for direct-API TTFT with a fast Claude model and no caching — [kunalganglani.com, 2026 LLM API Latency Benchmarks](https://www.kunalganglani.com/blog/llm-api-latency-benchmarks-2026)
- By contrast, Claude Haiku 5.5 variants measured with extended thinking enabled show TTFT of 8.19s (low) up to 310.72s (max) — these numbers reflect reasoning/"thinking" time baked into the TTFT measurement, not a comparable "fast conversational" configuration, and should not be read as a regression of the base model's raw streaming speed — [artificialanalysis.ai via kunalganglani.com summary](https://www.kunalganglani.com/blog/llm-api-latency-benchmarks-2026)
- **OpenCode server**: exposes REST session endpoints (`GET/POST /session`, `GET /session/:id`, etc.) plus an SSE events endpoint; the per-session `/event` SSE stream is described as "long-lived" and carries "incremental message parts, tool activity, and permission requests" — functionally analogous to the Agent SDK's partial-message stream — [opencode.ai, Server docs](https://opencode.ai/docs/server/); [zread.ai summary of OpenCode SSE integration](https://zread.ai/btriapitsyn/openchamber/12-server-sent-events-sse-integration)
- OpenCode has open reliability issues around its SSE transport: one issue reports the `/event` SSE endpoint failing to forward events to clients in a specific version (regression), another reports the SSE stream closing mid-turn despite being documented as persistent — i.e., similar "streaming is flaky in practice" pattern to the Claude Agent SDK issues above — [GitHub anomalyco/opencode#26866](https://github.com/anomalyco/opencode/issues/26866); [GitHub anomalyco/opencode#38458](https://github.com/anomalyco/opencode/issues/38458)
- **ACP**: prompt turn lifecycle is `session/prompt` (client→agent) → agent inserts message and returns a `messageId` → agent streams `session/update` notifications (message chunks, tool-call updates, state updates) → agent sends an idle `state_update` with a stop reason to signal completion. Explicitly, "acceptance means insertion," separate from actual processing/queuing — [agentclientprotocol.com, Prompt Lifecycle](https://agentclientprotocol.com/protocol/v2/prompt-lifecycle)
- ACP cancellation (`session/cancel`): the agent must "stop all language model requests and all tool call invocations as soon as possible," pending permission requests must be resolved with a `cancelled` response, and the agent reports completion via `idle`/`stopReason: "cancelled"`; the client should preemptively mark tool calls as `cancelled` when it sends the cancel notification — [agentclientprotocol.com, Prompt Lifecycle](https://agentclientprotocol.com/protocol/v2/prompt-lifecycle); also reflected in a real fix where Claude Code's ACP adapter was streaming deltas for a prompt that cancellation had already abandoned — [GitHub agentclientprotocol/claude-agent-acp#1313](https://github.com/agentclientprotocol/claude-agent-acp/pull/1313)
- ACP's spec explicitly disclaims latency guarantees: "The specification does not explicitly address latency metrics or time-to-first-update guarantees," only ordering/semantic guarantees (e.g., an initial `running` state_update may precede the prompt response; clients "cannot infer causality from timing alone") — [agentclientprotocol.com, Prompt Lifecycle](https://agentclientprotocol.com/protocol/v2/prompt-lifecycle)

### Inferences
- For a voice bridge, raw direct-API streaming (bypassing the Claude Code/Agent-SDK process) with a pre-warmed cached system prompt is the lowest-TTFT path when the task doesn't need the harness's tools; the TTFT cost of going through Claude Code/Agent SDK headless mode is a few hundred ms to ~2+ seconds of pure process/discovery overhead on top of identical underlying API latency, before any model generation starts.
- All three integration surfaces (Agent SDK partial messages, OpenCode SSE, ACP session/update) are architecturally capable of low-latency incremental delivery and mid-turn cancellation, but all three have *documented, currently-open* reliability bugs around streaming (buffering instead of incremental delivery, dropped SSE events, stream closing mid-turn). None of the three should be treated as production-hardened for strict TTFT guarantees as of this writing; empirical measurement against the exact SDK/server version in use is necessary before committing to a latency budget.
- Since subagent token deltas are not forwarded in the Agent SDK's partial-message stream, any pattern that delegates to a subagent for the "worker" role (see next section) will necessarily present as a single opaque "block" until that subagent's full message returns — reinforcing that the fast/slow split should happen at the orchestration layer (a separate fast model), not by relying on the harness's own subagent-streaming granularity.

### Gaps
- No controlled, apples-to-apples benchmark was found comparing Claude Agent SDK TTFT vs. raw Anthropic API TTFT vs. OpenCode server TTFT vs. ACP TTFT under identical prompts/caching conditions — the figures above are each from different measurement contexts and should not be directly subtracted from one another to produce a precise "harness overhead in ms" number. The report should state the overhead qualitatively (hundreds of ms to low seconds from process/discovery, on top of base model latency) rather than as one hard number.
- No data found specifically for OpenCode server's SSE time-to-first-event numbers (only architecture description, not measured latency).

## Architectural patterns for bridging a slow agent into a fast voice loop

### Takeaway
The proven pattern is a "talker-reasoner" / dual-model split: a fast, latency-tuned conversational model owns every turn and the microphone, while the slow agent harness runs as an independently-contexted background worker invoked via an async tool call; the fast model immediately acknowledges, keeps talking/fills silence, and later delivers the worker's result as a natural follow-up turn once it completes. This mirrors OpenAI Realtime's native "async tool calling" primitive and Pipecat's async function-call result-deferral mechanism.

### Cited Findings
- The **Talker-Reasoner architecture** (Google DeepMind, Christakopoulou et al. 2024) applies Kahneman's dual-system framing to agents: a "Talker" (System 1, fast/intuitive) manages all quick, seamless user/environment interaction, while a "Reasoner" (System 2, slow/deliberative) handles long-term reasoning and updates — [arXiv 2410.08328, Agents Thinking Fast and Slow](https://arxiv.org/pdf/2410.08328); summary at [Synced Review](https://syncedreview.com/2024/10/21/thinking-fast-and-slow-google-deepminds-dual-agent-architecture-for-smarter-ai/)
- LiveKit's production implementation: "Primary Agent" = fast model (example given: `google/gemma-4-31b-it`) handling every conversational turn and deciding when to delegate; "Subagent" = reasoning model (example: `google/gemini-3.1-pro`) with its own independent chat context doing the slow work in the background — [LiveKit, The talker-reasoner pattern for voice agents](https://livekit.com/blog/talker-reasoner-pattern-voice-agents)
- Problem statement without this pattern: "the user has to wait until the agent is done: two seconds of waiting, then three, until it starts to feel like a dropped call" — [LiveKit, talker-reasoner pattern](https://livekit.com/blog/talker-reasoner-pattern-voice-agents)
- Mechanism: the two models are connected via an async tool call; the tool's *first progress update* releases the conversation (the fast agent says "it's looking into it" and carries on with the user), and the subagent delivers its result "as a follow-up reply once it's idle, naming the question it answers" — [LiveKit, talker-reasoner pattern](https://livekit.com/blog/talker-reasoner-pattern-voice-agents)
- Filler/engagement strategy while the worker runs: the primary agent "keeps talking. Answers unrelated questions, asks clarifying ones, and voices periodic filler speech during silent stretches" — [LiveKit, talker-reasoner pattern](https://livekit.com/blog/talker-reasoner-pattern-voice-agents)
- Implementation is concrete, not just conceptual: LiveKit's Agents framework implements the primary agent as a standard `Agent` instance and the subagent as a separate `LLM` instance wired in via an async function tool — [LiveKit, talker-reasoner pattern](https://livekit.com/blog/talker-reasoner-pattern-voice-agents)
- **OpenAI Realtime API async tool calling**: setting `async: true` on a tool definition lets the model continue the conversation fluidly without waiting on that tool's result; "long-running function calls will no longer disrupt the flow of a session"; the model assigns a handle to each call that the app binds to the original `call_id` and the background job, keeping handles unique across the conversation — [OpenAI, Async tool calling guide](https://developers.openai.com/api/docs/guides/async-tool-calling); [OpenAI, Introducing gpt-realtime](https://openai.com/index/introducing-gpt-realtime/)
- Rationale given by OpenAI: this is specifically to prevent "long periods of silence" when a function takes real time to execute — [OpenAI Developer Community discussion](https://github.com/orgs/community/discussions/167399) (secondary, corroborating primary doc above)
- **Pipecat's equivalent primitive**: registering a function call with `cancel_on_interruption=False` makes it asynchronous — the LLM continues the conversation immediately without waiting for the result, and the result is injected later via a developer message. If the result arrives *before* the conversation has moved on, it settles in place exactly like a synchronous call (no visible deferral); if anything else happens first (user message, assistant text, another developer message), the result is deferred and delivered as a new message when ready. Pipecat also exposes `FunctionCallResultProperties(is_final=False)` for sending intermediate/progress updates on an async call — [Pipecat docs, Function Calling](https://docs.pipecat.ai/pipecat/learn/function-calling); corroborated by a related PR note: "Only defer an async tool result when the context shows the conversation moved on" — [GitHub pipecat-ai/pipecat#5705](https://github.com/pipecat-ai/pipecat/pull/5705)
- A dual-agent pattern also appears in retrieval-latency work: VoiceAgentRAG (Salesforce) uses a background "Slow Thinker" that predicts likely follow-ups and pre-fetches into a semantic cache, while a foreground "Fast Talker" reads only from that sub-millisecond cache — reported to cut voice RAG retrieval latency by 316x in their benchmark — [MarkTechPost, Salesforce VoiceAgentRAG](https://www.marktechpost.com/2026/03/30/salesforce-ai-research-releases-voiceagentrag-a-dual-agent-memory-router-that-cuts-voice-rag-retrieval-latency-by-316x/); paper at [arXiv 2603.02206](https://arxiv.org/html/2603.02206v2)

### Inferences
- For bridging Claude Code/Agent SDK, OpenCode, or an ACP agent as the "brain," the directly transferable pattern is: run the voice-facing conversational model as the Realtime/Pipecat "Talker," and wrap the harness invocation (headless `claude -p` run, OpenCode `session/prompt`, or ACP `session/prompt`) as a single async tool call from the Talker's perspective. The harness's own internal tool calls, file reads, and multi-turn agentic loop become invisible plumbing inside that one async call — the Talker never needs to narrate the harness's internal tool-call stream (and per the TTFT section, subagent-level deltas aren't even forwarded by the Agent SDK, reinforcing that this opacity is also a given constraint, not just a design choice).
- Progress updates surfaced to the user ("still looking into it," "found the file, checking now") should be synthesized by the Talker from coarse state signals (e.g., ACP's `state_update: running` / `requires_action`, or an Agent SDK tool-call-start event), not by reading harness output aloud — directly matching the brief's requirement to summarize for speech and never read code aloud. This is a design implication from the pattern, not something the sources state explicitly for Claude's harnesses specifically — flagged as inference, not citation.
- Permission prompts (a known ACP/Agent-SDK primitive — ACP's `requires_action`/pending permission request, Agent SDK's permission callbacks) map naturally onto the Talker's turn-taking loop: the harness's permission request should pause the background job and have the Talker ask the user a short yes/no question, then route the answer back as the tool's resumed input — this is an architectural extrapolation from the ACP cancellation semantics above (pending permission requests must be explicitly resolved, including on cancel) rather than a pattern explicitly documented for voice in the sources found.

### Gaps
- No source specifically describes "handling permission prompts by voice" as a named/documented pattern; the recommendation above is an inference from ACP's permission-request semantics plus the talker-reasoner pattern, not a cited existing implementation.
- No source was found directly benchmarking the added latency of routing through a full agent-harness (vs. a plain reasoning LLM) as the "Reasoner"/"Subagent" role in the talker-reasoner pattern — the LiveKit writeup uses a plain reasoning LLM (gemini-3.1-pro) as its subagent example, not an agentic harness with tool use, so harness-specific background-latency numbers are not available from this source.

## Local small LLM (M1 / RTX 3070) as the fast conversational layer vs. fast cloud model (Claude Haiku) via the harness

### Takeaway
Both M1 (16GB+ unified memory) and an RTX 3070 (8GB VRAM) comfortably run a Qwen3-4B or Qwen3-8B Q4 model as the fast "Talker" layer alongside local STT+TTS, at interactive token rates (~18-30 tok/s), but a cloud model like Claude Haiku reached via the harness avoids the memory contention and quality/latency trade-off of squeezing STT+TTS+LLM onto the same device, at the cost of network RTT and per-request cost. No source directly compared the two in a combined voice-pipeline memory/latency benchmark, so this is primarily an inference from separately-sourced component numbers.

### Cited Findings
- Qwen3-8B (8.2B params) runs "comfortably" on Apple Silicon with as little as 16GB unified memory; the default Ollama Qwen3-8B build is a 5.2GB download; on M1/M2 with 16GB RAM, Qwen3-8B at Q4 delivers ~18 tok/s — [codersera.com, Run Qwen3-8B on Mac](https://codersera.com/blog/run-qwen-3-8b-on-mac-an-installation-guide/)
- Qwen3-4B at Q4_K_M is ~2.5GB — notably lighter, leaving more headroom for STT/TTS models running concurrently — [llmhardware.io / spheron.network, Qwen3 hardware requirements summaries](https://llmhardware.io/guides/qwen3-hardware-requirements)
- On RTX 3070 (8GB VRAM): Qwen3-8B at Q4 needs ~5GB and runs well, delivering 20-30 tok/s; another source puts Q4_K_M VRAM usage at ~6.5GB, leaving only ~0.7GB for KV cache (limiting usable context length); a dedicated RTX 3070 guide states it's suitable for "7B-8B only" models at an estimated 61 tok/s — [modelfit.io, RTX 3070 8GB for Local LLMs](https://modelfit.io/gpu/rtx-3070/); [willitrunai.com, Qwen 3 GPU requirements](https://willitrunai.com/blog/qwen-3-gpu-requirements)

### Inferences
- The 8GB VRAM ceiling on an RTX 3070 is the binding constraint: Qwen3-8B Q4 alone consumes 5-6.5GB, leaving only 1.5-3GB for a local STT model (e.g., Whisper-small/medium) and a local TTS model running concurrently — on this hardware, a smaller Qwen3-4B (~2.5-3GB) is the safer choice to leave adequate headroom for STT+TTS without context-length starvation, trading some conversational quality for pipeline stability.
- On an M1 with 16GB unified memory, the same contention exists but unified memory makes the trade-off softer (no hard VRAM wall, but system-wide memory pressure from STT+TTS+OS); 24GB+ configurations give comfortable headroom per the Qwen3-8B guidance above.
- A fast cloud model (Claude Haiku) via direct API avoids this memory contention entirely and offloads compute, but reintroduces network RTT and the per-call cost/latency variance noted in the TTFT section (plain Haiku ~600ms TTFT is already higher than a local 4B/8B model's effective "first token" time on decent hardware, though local token/sec throughput for generation is typically much lower than a cloud API's). The right choice depends on whether the bottleneck is perceived as "time to start speaking" (favor local, near-instant first token on a small warm model) or "quality/coherence of the fast layer's small talk and intent parsing" (favor cloud Haiku).

### Gaps
- No source was found running an actual end-to-end combined benchmark (STT + small local LLM + TTS all resident simultaneously on M1 or RTX 3070) measuring realized voice-to-voice latency or memory headroom — all figures above are per-component, not from a combined voice-pipeline deployment, so the "advisable" question cannot be answered with a measured number, only reasoned about from component specs.
- No comparative TTFT number for Qwen3-4B/8B via Ollama/llama.cpp/MLX was found (only tokens/sec generation throughput) — first-token latency specifically for these local models, which is what matters most for the "fast talker" role, is a gap.

## Echo cancellation / barge-in for laptop speaker+mic, and headset recommendations

### Takeaway
WebRTC's AEC3 (and macOS's equivalent native VoiceProcessingIO/AVAudioEngine voice-processing mode) can cancel most speaker-into-mic echo but reliably struggles during "double-talk" (user and agent speaking simultaneously, i.e. barge-in) and needs a multi-second warm-up/convergence period; for a laptop speaker+mic setup this materially risks false suppression of the user's barge-in speech, so a headset (physically separating playback from the mic) remains the more robust recommendation for this use case, though no source gave a specific headset model recommendation.

### Cited Findings
- WebRTC's modern echo canceller, AEC3, is the default in the pipeline; it models how the room and speaker-to-mic acoustic path delay/distort the reference signal and subtracts the predicted echo from the mic signal — [salivity.github.io, WebRTC Audio Echo Cancellation Explained](https://salivity.github.io/webrtc/article/webrtc-audio-echo-cancellation-explained)
- WebRTC AEC "struggles when the user is on speakerphone, because the speaker output is loud, the microphone is sensitive, and the acoustic coupling between them is strong" — AEC reduces but does not eliminate echo in this configuration — [coval.ai, Voice AI Echo Cancellation](https://www.coval.ai/blog/voice-ai-echo-cancellation/)
- Double-talk (simultaneous user+agent speech, i.e. barge-in) is AEC's hardest case: "false suppression of user speech during double-talk is a common AEC failure mode"; AEC3 mitigates this by monitoring coherence/energy between reference and mic signal and freezing filter adaptation when double-talk is detected, to prevent the filter diverging — [coval.ai, Voice AI Echo Cancellation](https://www.coval.ai/blog/voice-ai-echo-cancellation/)
- Browser-embedded AEC needs "a few seconds of training on speaker and mic audio before it can cancel echoes reliably"; a documented workaround is to delay transmitting mic audio for a few seconds after `getUserMedia()` to let the built-in AEC converge first — [coval.ai, Voice AI Echo Cancellation](https://www.coval.ai/blog/voice-ai-echo-cancellation/)
- On macOS, native AEC is accessed via Core Audio's VoiceProcessingIO or, at a higher level, `AVAudioEngine`'s `inputNode.setVoiceProcessingEnabled(true)` — both share the same underlying technology/limitations; AVAudioEngine handles the input/output configuration automatically, while VoiceProcessingIO requires manual Audio Unit setup — [Apple Developer Forums, Using VoiceProcessingIO for echo cancellation on macOS](https://developer.apple.com/forums/thread/66953)
- Apple's native voice processing provides "best-in-class audio signal processing, including echo cancellation, noise suppression, and automatic gain control," with performance "tuned by acoustic engineers for each Apple product model" — but critically, it "works only when input and output run on the same engine" (i.e., both routed through the voice-processing-enabled AVAudioEngine instance, not mixed with a separate playback path) — [Apple Developer Forums](https://developer.apple.com/forums/thread/66953)

### Inferences
- For a laptop built-in speaker+mic setup, both WebRTC AEC3 and macOS's native VoiceProcessingIO are architecturally capable of handling the basic echo-cancellation case, but the double-talk/barge-in failure mode (false-suppressing the user's interrupting speech) is a direct risk to the project's interruption/barge-in requirement — the convergence delay (multi-second warm-up) also means the very start of a conversation is the most echo/barge-in-fragile window, which matters for a voice UI that should support interrupting the agent immediately.
- Given this, a headset (even a basic wired one) sidesteps the hardest failure mode entirely by eliminating the acoustic coupling AEC has to model, and should be the default recommendation for reliable barge-in; built-in speaker+mic should be treated as a "works most of the time, degrades during interruption" fallback, with the mic-transmission-delay workaround applied to let AEC converge before the user's first utterance if speaker+mic is used.
