## Research Findings: Open-Source Speech-to-Speech / Full-Duplex Voice Models

### 1. Kyutai Moshi
- **Repo/license**: [kyutai-labs/moshi](https://github.com/kyutai-labs/moshi) — code MIT/Apache-2.0, weights CC-BY 4.0. Last push (GitHub API `pushed_at`): 2026-09-09.
- **Architecture**: True end-to-end speech-to-speech. Moshi is built on a 7B "Helium" temporal transformer + Mimi neural codec, with an "inner monologue" where text-token prediction happens *inside* the same model stream as audio generation, not as a separable preprocessing/postprocessing step. [Source](https://github.com/kyutai-labs/moshi)
- **Reasoning swap-out?** No. No mechanism for routing to an external LLM/agent is documented; the reasoning is fused with audio generation in a single multi-stream transformer. [Source](https://github.com/kyutai-labs/moshi)
- **Self-hostable / hardware**: Yes. PyTorch backend needs a GPU with ~24GB VRAM; MLX port runs on Apple Silicon (tested on M3 MacBook Pro); Rust/CUDA backend needs NVIDIA toolkit w/ `nvcc`. [Source](https://github.com/kyutai-labs/moshi)
- **Analysis (inference)**: Moshi is architecturally the opposite of what's needed — it's a sealed, monolithic speech-text model whose "brain" cannot be swapped for an external agent harness without retraining/forking the model. Not a fit for a bring-your-own-agent requirement.

### 2. Kyutai Unmute
- **Repo/license**: [kyutai-labs/unmute](https://github.com/kyutai-labs/unmute) — MIT license. Last push: 2026-09-09. [Source](https://github.com/kyutai-labs/unmute)
- **Distinction from Moshi (confirmed)**: Unmute is explicitly *not* an end-to-end model — it's a wrapper that bolts Kyutai's own low-latency STT and TTS around an arbitrary external text LLM. Tagline: "Make text LLMs listen and speak." [Source](https://github.com/kyutai-labs/unmute)
- **Mechanism (confirmed, exact)**: Literally "bring your own LLM via an OpenAI-compatible API." Config is via env vars `KYUTAI_LLM_URL`, `KYUTAI_LLM_MODEL`, `KYUTAI_LLM_API_KEY`; default local backend is vLLM, but it also works with OpenRouter, Ollama, or any OpenAI-compatible endpoint. [Source](https://github.com/kyutai-labs/unmute)
- **Tool-calling / agent harness fit**: Tool-calling is explicitly called out as unimplemented in Unmute itself, with the README's own recommendation: "The easiest way to integrate tool calling into Unmute would be to do so in a way that's fully invisible to Unmute itself — just make it part of the LLM server." [Source](https://github.com/kyutai-labs/unmute) This means a Claude Agent SDK / OpenCode server could sit behind the OpenAI-compatible endpoint, as long as it can stream a response back fast enough and present itself as a single "LLM" completion call.
- **Hardware**: GPU with CUDA, min 16GB VRAM, x86_64, Linux or Windows/WSL (no native macOS/ARM). Per-service VRAM: STT 2.5GB, TTS 5.3GB, default LLM (Gemma 3 1B) 6.1GB. [Source](https://github.com/kyutai-labs/unmute)
- **Analysis (inference)**: This is the best-fitting candidate in the set for the stated requirement. It genuinely separates STT/TTS/turn-taking from the "brain," and the brain is just whatever answers an OpenAI-style `/chat/completions` call — Claude Agent SDK or an OpenCode server exposing an OpenAI-compatible endpoint would plug in directly, no model surgery needed. The caveat (my inference, not sourced) is latency/turn-taking: Unmute's STT/TTS loop is tuned for sub-second turnaround (~450ms round trip cited in the architecture description); a multi-second agentic tool-calling turn (e.g., Claude Agent SDK doing multi-step planning/tool use) would blow through Unmute's expected turn-taking window unless Unmute's VAD/barge-in logic is tolerant of long silences — the README doesn't document behavior under multi-second LLM latency, so this is a gap, not a confirmed limitation.

### 3. Ultravox (fixie-ai/ultravox)
- **Repo/license**: [fixie-ai/ultravox](https://github.com/fixie-ai/ultravox) — MIT license. Last push (GitHub API): 2025-12-12 (v0.7 release line). [Source](https://github.com/fixie-ai/ultravox)
- **Modality (verified)**: Speech-in, text-out. Confirmed: "emits streaming text," with the README noting speech-out ("stream of speech tokens") as a future direction, not current functionality. [Source](https://github.com/fixie-ai/ultravox)
- **Architecture**: Frozen audio encoder + frozen LLM backbone (default Llama 3.3 70B, 8B variant also published) + trainable multimodal adapter/projector that feeds audio embeddings directly into the LLM's input space, bypassing separate ASR. [Source](https://github.com/fixie-ai/ultravox)
- **Reasoning swap-out?** Partially. Because the LLM backbone is "frozen" and the adapter is trained for a specific backbone, you can't trivially point it at an arbitrary agent process; swapping the LLM means re-pairing/re-training the adapter for that backbone. However, since output is plain text (not audio), a downstream system — including Claude Agent SDK — can consume that text and do its own reasoning/tool-use, with TTS/output handled entirely outside Ultravox. The "brain swap" would happen *after* Ultravox's own LLM already produced text, not instead of it, unless you fork/retrain.
- **Hardware**: Training used 8×H100 GPUs (2-3 hours for 14K steps); inference requirements not detailed in README excerpt fetched. [Source](https://github.com/fixie-ai/ultravox)
- **Analysis (inference)**: Ultravox is not full-duplex speech-to-speech (no native audio out in the open-source repo) and its LLM is baked into the model via the adapter, so it's not a clean "intercept the reasoning step" architecture. It could be used as an upstream speech-understanding component feeding an external agent, but that requires discarding Ultravox's own generated text/response and only using it for transcription-plus-context, which is a workaround rather than a designed integration point. Fixie's commercial "Ultravox Realtime" platform (ultravox.ai) is mentioned as having an agent-building layer, but that's a hosted product, not confirmed as open-source or inspected here — gap.

### 4. Sesame CSM (SesameAILabs/csm)
- **Repo/license**: [SesameAILabs/csm](https://github.com/SesameAILabs/csm) — Apache-2.0. Last push (GitHub API): 2025-05-27. [Source](https://github.com/SesameAILabs/csm)
- **Modality**: Not speech-to-speech reasoning at all — it's a conditional TTS/audio-generation model. Explicitly documented: "CSM is trained to be an audio generation model and not a general-purpose multimodal LLM. It cannot generate text," and users are told to "employ a separate LLM for text generation." [Source](https://github.com/SesameAILabs/csm)
- **Architecture**: Llama-backbone + smaller audio (Mimi-code) decoder; two Llama-style autoregressive decoders (backbone predicts first codebook token, depth decoder predicts the rest). [Source](https://github.com/SesameAILabs/csm)
- **Reasoning swap-out?** By design, yes — CSM only does audio generation conditioned on text/context; the "brain" is explicitly external and already expected to be supplied by the integrator. This is structurally closer to a TTS engine (plus a context-aware/paralinguistic generation layer) than a full agent-loop component.
- **Hardware**: CUDA 12.4/12.6-tested GPU, Python 3.10, FFmpeg; requires access to gated Llama-3.2-1B and CSM-1B checkpoints. [Source](https://github.com/SesameAILabs/csm)
- **Analysis (inference)**: CSM is not a full-duplex speech-to-speech system and shouldn't be compared 1:1 with Moshi/Unmute — it's best understood as a high-quality, conversationally-aware TTS backend that could sit alongside a separate STT and any external agent harness (similar role to Unmute's TTS piece, but without Unmute's integration scaffolding, VAD, or turn-taking logic already wired up).

### 5. Hugging Face speech-to-speech (huggingface/speech-to-speech)
- **Repo/license**: [huggingface/speech-to-speech](https://github.com/huggingface/speech-to-speech) — Apache 2.0. Last push (GitHub API): 2026-10-29 (actively maintained, 14k★/1.7k forks). [Source](https://github.com/huggingface/speech-to-speech)
- **Explicit framing**: "an effort for an open-sourced and modular GPT-4o." [Source](https://github.com/huggingface/speech-to-speech)
- **Architecture**: Four independent, queue-connected stages: (1) Silero VAD v5 for turn-taking, (2) STT, (3) LLM ("generates the response, streaming text and tool calls"), (4) TTS. [Source](https://github.com/huggingface/speech-to-speech)
- **Reasoning swap-out?** Yes, explicitly and flexibly — more flexible than Unmute's single OpenAI-compatible-endpoint model. The LLM stage supports local Transformers, MLX (macOS), llama.cpp servers, OpenAI-compatible APIs, or hosted providers (e.g., OpenRouter), and the docs describe users being able to "move only the LLM to a provider" while keeping speech local. Because the LLM stage already natively streams "text and tool calls," this is architecturally the most agent-harness-friendly of the cascaded systems reviewed, provided the custom harness can conform to (or be adapted to) one of its supported backend interfaces. [Source](https://github.com/huggingface/speech-to-speech)
- **Hardware**: Apple Silicon ~16GB unified memory recommended; Linux/NVIDIA ~24GB VRAM for the default pipeline; CPU-only possible but "slow replies." [Source](https://github.com/huggingface/speech-to-speech)
- **Latency**: Per-response logging of STT, LLM, first-TTS-audio, and total speech-to-audio durations; "Smart Turn" endpointing uses content+prosody with an 800ms default grace period and a 2-second max hold for incomplete turns. [Source](https://github.com/huggingface/speech-to-speech)
- **Analysis (inference)**: The 2-second max-hold-for-incomplete-turn ceiling (as documented) strongly suggests this pipeline is tuned for single-shot LLM replies, not multi-second/multi-step agentic tool-calling turns. A Claude Agent SDK turn involving several tool calls could easily exceed that window, likely triggering premature turn-end/interruption handling unless the turn-taking logic is reconfigured or bypassed — this is my inference from the documented default values, not a confirmed failure mode (no direct documentation of long-agentic-turn behavior was found — gap).

### 6. Qwen-Omni family (Alibaba)
- **Qwen2.5-Omni**: [Qwen/Qwen2.5-Omni-7B](https://huggingface.co/Qwen/Qwen2.5-Omni-7B) — Apache 2.0, paper dated March 26, 2025 (arXiv 2503.20215 per search). [Source](https://huggingface.co/Qwen/Qwen2.5-Omni-7B) True end-to-end: audio/text/image/video in, text + natural speech out, via a "Thinker-Talker" architecture (Thinker = 7B dense text LLM producing text tokens + hidden states; Talker = DiT-based audio decoder conditioned on those hidden states). [Source](https://github.com/PengHu645/Qwen2.5-Omni) VRAM: BF16 + FlashAttention2, 31GB for 15s video context up to 60GB for 60s video (real usage ~1.2x higher); `model.disable_talker()` saves ~2GB if audio output isn't needed. [Source](https://huggingface.co/Qwen/Qwen2.5-Omni-7B)
- **Qwen3-Omni**: [QwenLM/Qwen3-Omni](https://github.com/QwenLM/Qwen3-Omni), Apache 2.0, "fully open source," any-to-any multimodal, released ~Sept 2025. [Source](https://github.com/QwenLM/Qwen3-Omni)
- **Qwen3.5-Omni**: Per [arXiv 2604.15804](https://arxiv.org/abs/2604.15804) (Qwen3.5-Omni Technical Report, dated 2026-04-22) this is a much larger (hundreds of billions of params) MoE Thinker-Talker model with native agentic behavior (autonomous WebSearch, FunctionCall invocation). However, per [WinBuzzer reporting](https://winbuzzer.com/2026/03/31/alibaba-qwen35-omni-closed-source-multimodal-ai-xcxwbn/), Alibaba kept Qwen3.5-Omni **closed-source** — no released weights or license — reportedly tied to a monetization pivot in Alibaba Cloud. The article does not explicitly confirm whether Qwen2.5-Omni/Qwen3-Omni remain open (gap), but no retraction/delisting of those Apache-2.0 releases was found.
- **Reasoning swap-out?** The Thinker-Talker split is architecturally a separable reasoning/speech-generation boundary (Thinker's hidden states condition the Talker), and `disable_talker()` shows the components can at least be partially decoupled. However, no documentation was found of a supported way to replace the Thinker with an *external* agent process while keeping the Talker for audio synthesis — the hidden-state conditioning between Thinker and Talker is an internal interface, not an exposed API like Unmute's OpenAI-compatible boundary. Treat "could be adapted via a research fork" as inference, not a documented feature.
- **Analysis (inference)**: For the open Qwen2.5-Omni/Qwen3-Omni models, the Thinker-Talker coupling is tighter than Unmute's or HF speech-to-speech's cascaded designs — it's plausible but unverified that one could swap the Thinker for a custom agent by feeding the Talker differently, but this would require non-trivial model surgery, not a supported integration point. The newest, most agent-capable variant (3.5) is now closed-source, which cuts against using the Qwen-Omni line for a requirement centered on bring-your-own swappable agent harness.

### Other notable 2025-2026 full-duplex models found
- **NemotronLabs VoiceChat** ([arXiv 2609.21967](https://arxiv.org/abs/2609.21967), ~Sept 2026): Described as "an open full-duplex speech-to-speech model" with native tool-calling — specialized output streams for agent text vs. structured function calls, plus an RNN-T branch for incremental transcription and a streaming TTS decoder. Abstract bears a CC-BY 4.0 icon. **Gap**: no GitHub/Hugging Face link or explicit code/weight release found in the fetched content — cannot confirm actual availability/license terms beyond the abstract icon. [Source](https://arxiv.org/abs/2609.21967) If genuinely released, this is architecturally the closest match in the entire survey to "fused but tool-call-aware full-duplex," though note it bakes tool-calling into the model itself rather than deferring to an arbitrary external harness — the opposite design philosophy from Unmute.

### Cross-model synthesis (analysis/inference, not sourced)
- The clearest axis in this set is "cascaded, pluggable-LLM pipeline" (Unmute, HF speech-to-speech) vs. "fused single-model" (Moshi, Qwen-Omni family, NemotronLabs VoiceChat) vs. "single-purpose component" (Ultravox = speech-in/text-out encoder, CSM = TTS-only decoder).
- Only Unmute and HF speech-to-speech expose a documented, swappable LLM boundary compatible with an external agent harness (OpenAI-compatible API / pluggable backend list respectively). Of the two, Unmute's boundary is narrower/cleaner (single OpenAI-compatible endpoint) while HF speech-to-speech's is more flexible but has a documented turn-taking grace window (800ms/2s) that is a plausible friction point for multi-second agentic tool-use turns — this specific risk is inferred from documented defaults, not confirmed by either project's own text.
- Fused end-to-end models (Moshi, Qwen-Omni, likely NemotronLabs VoiceChat) are fundamentally in tension with a bring-your-own-harness requirement: their "reasoning" is either literally inside the same transformer producing audio tokens (Moshi) or conditions a downstream audio decoder via internal hidden states (Qwen-Omni's Thinker→Talker), neither of which is an externally addressable interface a Claude Agent SDK process could hook into without retraining or model surgery.
