## VAD and Turn-Detection Models for Real-Time Local Voice Agents

### Silero VAD
- **Architecture**: Small RNN — STFT front-end (Conv1d, 1→258 channels) → 4× Conv1d+ReLU encoder → LSTM (hidden size 128, carries state across chunks) → Conv1d decoder with sigmoid output. [Silero VAD GitHub](https://github.com/snakers4/silero-vad)
- **Size**: ~309K parameters, JIT model ~1.2–2 MB on disk. [snakers4/silero-vad](https://github.com/snakers4/silero-vad), [soniqo.audio guide](https://soniqo.audio/guides/vad)
- **Memory/compute**: Repo states "1G+ RAM," runs on a "modern CPU with AVX/AVX2/AVX-512/AMX" — no GPU required. Optional GPU via ONNX Runtime claimed up to 4-5x faster, but not needed. [snakers4/silero-vad](https://github.com/snakers4/silero-vad)
- **Latency**: Processes 512-sample (32ms @16kHz) chunks; repo claims <1ms per 30ms+ chunk on a single CPU thread; one report cites 0.75ms per-chunk latency on M1 Max. [snakers4/silero-vad](https://github.com/snakers4/silero-vad)
- **Semantic vs acoustic**: Purely acoustic/energy-pattern based speech-presence detector — no linguistic/turn-completion understanding.
- **Language support**: Trained on audio from "6000+ languages" (acoustic, language-agnostic by design, so English/German both fine as speech-presence detection). [snakers4/silero-vad](https://github.com/snakers4/silero-vad)
- **License**: MIT. [snakers4/silero-vad](https://github.com/snakers4/silero-vad)
- **Maintenance**: Actively developed (v6.x era); exact 2025/2026 release dates not confirmed in fetched content — not found.

### TEN VAD (TEN framework)
- **Architecture**: Not fully disclosed; appears to be a lightweight acoustic model using pitch-estimation techniques derived from LPCNet (`pitch_est.cc`), not a classic GMM and not described as a transformer. Exact architecture family: not found. [TEN-framework/ten-vad](https://github.com/ten-framework/ten-vad)
- **Size**: 324 KB standard ONNX, 126 KB int8-quantized; native library sizes 277 KB (Web/M1) to 731 KB (macOS M1), 306 KB (Linux), 464-508 KB (Windows). Parameter count not disclosed. [sherpa ten-vad docs](https://k2-fsa.github.io/sherpa/onnx/vad/ten-vad.html), [GitHub](https://github.com/ten-framework/ten-vad)
- **Memory/compute**: Described as having "lower computational complexity and smaller library size than Silero VAD"; CPU-only, no GPU needed. [GitHub](https://github.com/ten-framework/ten-vad)
- **Latency**: Real-time-factor (RTF) benchmarks: 0.0150 (AMD Ryzen, Linux), 0.0086 (Xeon Platinum, Linux), 0.0160 (macOS M1), 0.010 (Web/M1) — i.e., roughly 60-150x faster than real time on these CPUs. [GitHub](https://github.com/ten-framework/ten-vad)
- **Accuracy**: Vendor claims best precision-recall performance vs WebRTC VAD and Silero VAD on annotated LibriSpeech/GigaSpeech/DNS-Challenge test sets. [GitHub](https://github.com/ten-framework/ten-vad); an independent arXiv benchmark paper exists ("Window Size Matters: Benchmarking VAD in Noise," [arxiv.org/html/2610.14607](https://arxiv.org/html/2610.14607)) but I did not fetch its numbers.
- **Semantic vs acoustic**: Pure acoustic VAD, not a semantic/turn-completion model — language-agnostic by nature.
- **Language support**: Not a linguistic model; German/English irrelevant distinction — not found any language-specific limitation.
- **License**: Apache 2.0, with `pitch_est.cc` carrying BSD-2/3-Clause terms from LPCNet. [GitHub](https://github.com/ten-framework/ten-vad)
- **Maintenance**: Latest release v1.0.6.8 on 2025-11-14 (per PyPI); 115+ commits, actively developed with recent WASM/Java/Go binding additions. [PyPI ten-vad](https://pypi.org/project/ten-vad/)

### Pipecat Smart Turn (v2 and v3, Daily/Pipecat)
- **v2 architecture**: wav2vec2 encoder backbone + shallow linear classifier head, 94.8M parameters, ~360MB safetensors checkpoint (~400MB overall footprint). Inference ~12ms on an NVIDIA L40S GPU (3x faster than v1). [Daily blog: Smart Turn v2](https://www.daily.co/blog/smart-turn-v2-faster-inference-and-13-new-languages-for-voice-ai/), [HF pipecat-ai/smart-turn-v2](https://huggingface.co/pipecat-ai/smart-turn-v2)
- **v3 architecture**: Whisper-Tiny encoder layers + linear classifier, native-audio (direct PCM, no transcript), int8 static QAT. ~8M parameters, 8MB (int8) or 32MB (fp32). ~50x smaller than v2. [Daily blog: Smart Turn v3](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/)
- **Latency (v3)**: 12ms on modern CPU (AWS c7a.2xlarge); 15.2ms on c8g.2xlarge; 59.8ms on cheap c8g.medium; ~65ms on Pipecat Cloud standard 1x instance; 3.3–6.6ms on various NVIDIA GPUs (GPU gives only ~1% accuracy bump, not required). [Daily blog](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/)
- **Accuracy (v3)**: English — 94.31% accuracy, 2.64% false-positive, 3.06% false-negative. German — 96.14% accuracy, 2.50% FP, 1.36% FN. v3 "maintains or improves accuracy across all languages vs v2" despite the size cut. v3.1 improved accuracy via larger human-audio dataset + better quantization; v3.2 cut short-utterance miscategorization by 40%. [Daily blog v3](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/), [v3.1 post](https://www.daily.co/blog/improved-accuracy-in-smart-turn-v3-1/), [v3.2 post](https://www.daily.co/blog/smart-turn-v3-2-handling-noisy-environments-and-short-responses/)
- **Semantic vs acoustic**: True semantic turn detector — operates on raw audio (prosody + implied linguistic completeness), not transcript text, to judge whether the speaker intends to yield the turn.
- **Language support**: v3 covers 23 languages including English and German explicitly. [Daily blog](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/)
- **License**: Fully open source — weights, training data, and training code released; BSD-2-Clause per one fetched source. [GitHub pipecat-ai/smart-turn](https://github.com/pipecat-ai/smart-turn)
- **Maintenance**: Very active — v3 (2026), v3.1, v3.2 all shipped in quick succession as of late 2026. [Daily blog posts above]
- **Pipeline/layering**: Runs downstream of a lightweight VAD (e.g., Silero): VAD detects silence/pause; only then does Smart Turn process the buffered utterance (up to 8s) to decide if it's a real end-of-turn. Because it only fires on VAD-triggered pauses (not continuously), the added compute cost is minimal — essentially one extra ~12-65ms CPU inference per candidate pause, not a continuous per-frame cost. [Daily blog](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/)

### LiveKit Turn Detector
- **Architecture**: Two generations —
  - Legacy **text turn detector**: fine-tuned Qwen2.5-0.5B-Instruct, operating on ASR transcript text (now deprecated in favor of audio model). [docs.livekit.io turn-detector](https://docs.livekit.io/agents/logic/turns/turn-detector/)
  - Current **audio turn detector v1 / v1-mini**: dual-branch design — a semantic branch (audio encoder + learned adapter + fine-tuned LM) and an acoustic branch (timing/prosody), fused into one end-of-turn prediction. [LiveKit blog: Solving end-of-turn detection](https://livekit.com/blog/solving-end-of-turn-detection)
- **Size**: Text model: 396MB disk, Qwen2.5-0.5B base. Audio v1/v1-mini: parameter count/size not disclosed in fetched sources — not found.
- **Memory**: Text detector needs <500MB RAM, recommended on compute-optimized (non-burstable) instances like AWS c6i/c7i. v1-mini explicitly optimized for local CPU inference; full v1 served via LiveKit Cloud's optimized inference (not necessarily local-runnable). [docs.livekit.io](https://docs.livekit.io/agents/logic/turns/turn-detector/)
- **Latency**: Text detector: ~50-160ms per turn, ~1s prediction timeout. Audio model latency/false-cutoff tradeoff curve: 9.9% false-cutoff at 300ms budget, 4.5% at 600ms; at a 5% false-cutoff target mean latency is 543ms, at 10% target it's 295ms. [docs.livekit.io](https://docs.livekit.io/agents/logic/turns/turn-detector/), [LiveKit blog](https://livekit.com/blog/solving-end-of-turn-detection)
- **Accuracy**: Audio v1 reported to outperform Deepgram Flux, ultraVAD, and Soniox on latency/false-cutoff tradeoff; described as "strongest overall multilingual model." Earlier generation cut unwanted interruptions by 39% vs prior approach. [LiveKit blog](https://livekit.com/blog/solving-end-of-turn-detection), [blog.livekit.io 39% post](https://blog.livekit.io/improved-end-of-turn-model-cuts-voice-ai-interruptions-39/)
- **Semantic vs acoustic**: Explicitly semantic + acoustic fusion (not pure silence-based).
- **Language support**: 14 languages for audio detector (English, Arabic, **German**, Spanish, French, Hindi, Indonesian, Italian, Japanese, Korean, Dutch, Portuguese, Turkish, Chinese); text detector covers same 14 plus Russian (15). German is explicitly supported. [docs.livekit.io](https://docs.livekit.io/agents/logic/turns/turn-detector/)
- **License**: Code Apache-2.0; model weights under "LiveKit Model License" (not a fully open license); full v1 model free only when hosted on LiveKit Cloud (i.e., not simply self-hostable for free). [docs.livekit.io](https://docs.livekit.io/agents/logic/turns/turn-detector/)
- **Pipeline/layering**: Requires VAD minimum-silence-duration ≥250ms (Silero's default 0.55s satisfies this); VAD triggers the candidate pause, turn detector then confirms/overrides. With audio turn detection enabled, LiveKit reduces its endpointing `min_delay` to 0.3s and `max_delay` to 2.5s (vs 0.5s/3.0s defaults). [docs.livekit.io](https://docs.livekit.io/agents/logic/turns/turn-detector/)

### Kyutai Semantic VAD (part of Delayed Streams Modeling / Moshi STT)
- **Architecture**: A VAD signal derived internally from Kyutai's streaming STT model (`kyutai/stt-1b-en_fr`, ~1B params, 12.5Hz frame rate, built on the Mimi streaming codec + Moshi-style text/audio stream model), rather than a standalone small model — i.e., semantic VAD is a byproduct of the big streaming STT's text stream, not a separate lightweight classifier. [kyutai-labs/delayed-streams-modeling GitHub](https://github.com/kyutai-labs/delayed-streams-modeling)
- **Size/latency specific to the VAD component**: Not found — fetched sources (GitHub README, model card, arXiv abstract) only confirm the feature exists (`--vad` flag in the Rust inference binary) without isolating VAD-specific latency, parameter count, or memory footprint from the parent STT model's own figures (model is ~1B params, ~0.5s delay, 12.5Hz).
- **Memory/GPU**: Inherits the footprint of the full 1B-parameter streaming STT model (not a tiny bolt-on) — likely needs a GPU for comfortable real-time use given the 1B size, though this is an inference from model scale rather than a sourced number. Not confirmed.
- **Semantic vs acoustic**: True semantic end-of-turn signal, since it's computed from the model's internal text/language representation during streaming transcription, not simple silence detection.
- **Language support**: `kyutai/stt-1b-en_fr` covers English and French only — no German support found in the fetched model card. [HF kyutai/stt-1b-en_fr], [HF kyutai/stt-2.6b-en](https://huggingface.co/kyutai/stt-2.6b-en) (English-only variant also exists)
- **License**: Weights released under CC-BY 4.0. [kyutai-labs/delayed-streams-modeling](https://github.com/kyutai-labs/delayed-streams-modeling)
- **Maintenance**: Active; related arXiv preprint "Streaming Sequence-to-Sequence Learning with Delayed Streams Modeling" ([arxiv.org/abs/2509.08753](https://arxiv.org/abs/2509.08753)) posted 2025; detailed VAD latency/accuracy numbers not available in the fetched abstract — would require the full PDF, not retrieved here.
- **Pipeline/layering**: Not a separate "VAD then turn-detector" stage — it's an emergent signal from the STT model itself, so there's no additional model to layer on top, but you pay the cost of running the full 1B-param STT continuously rather than a cheap VAD gating a bigger model.

### WebRTC VAD (classic GMM-based)
- **Architecture**: Classic Gaussian Mixture Model. Splits 0-4kHz into 6 subbands (80-250Hz, 250-500Hz, 500Hz-1kHz, 1-2kHz, 2-3kHz, 3-4kHz), computes subband energy features, and classifies speech/non-speech probability via GMM with adaptive thresholds per aggressiveness mode. [chromium.googlesource.com vad_core.c](https://chromium.googlesource.com/external/webrtc/+/refs/heads/master/common_audio/vad/vad_core.c), [Alibaba Cloud topic writeup](https://topic.alibabacloud.com/a/webrtcs-voice-activity-detection-vad-algorithm_8_8_10267733.html)
- **Size/footprint**: Tiny, classic DSP-era code (no neural weights) — exact KB size not found, but is widely known to be a few hundred KB of C at most; negligible RAM. CPU-only, trivially runs on anything, including embedded devices.
- **Latency**: Supports 10/20/30ms frames (80/160/240 samples at 8kHz after downsampling); per-frame compute is sub-millisecond on any modern CPU (not explicitly benchmarked in fetched sources, but implied by its minimal GMM-on-energy-features design).
- **Accuracy**: Widely cited in newer papers (TEN VAD, Silero) as the baseline that both newer models beat on precision/recall, but WebRTC VAD's own numbers were not found in fetched sources — TEN VAD/Silero papers report they outperform it, numbers specific to WebRTC VAD itself not found.
- **Semantic vs acoustic**: Pure acoustic energy-based VAD, no semantic component, highest false-interruption rate of this entire list since it only tracks energy/spectral features.
- **Language support**: Language-agnostic signal-processing approach — not a language model.
- **License**: BSD-style (3-Clause), inherited from the WebRTC project overall.
- **Maintenance**: Maintained as part of the Google WebRTC codebase, but the VAD algorithm itself is legacy/frozen (no model to retrain); still widely used as a fallback baseline.

### Combining VAD + Semantic Turn Detector — typical layering and added cost
- Standard pattern across the ecosystem (explicit in both Pipecat and LiveKit docs): a cheap acoustic VAD (Silero, WebRTC, or TEN) runs continuously per-frame to detect speech presence and trigger interruption/barge-in; once VAD detects a pause of some minimum duration, a separate semantic model (Smart Turn, LiveKit's turn detector, or Kyutai's STT-internal signal) runs once on the buffered utterance to decide if the pause is a genuine end-of-turn or just a mid-sentence hesitation. [Daily blog Smart Turn v3](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/), [docs.livekit.io turn-detector](https://docs.livekit.io/agents/logic/turns/turn-detector/)
- Added latency/cost of layering a semantic detector on top of plain VAD: because the semantic model only runs once per candidate pause (not per frame), the added overhead is roughly one extra 10-65ms CPU inference per utterance boundary for Smart Turn v3, or ~50-550ms depending on target false-cutoff rate for LiveKit's audio model (that 50-550ms is largely intentional *waiting* time built into the latency/accuracy tradeoff curve, not pure compute cost). Both are explicitly designed to be CPU-only and run comfortably alongside the base VAD, unlike Kyutai's semantic VAD, which is inherent to a much larger (~1B param) streaming STT and therefore carries that model's full compute/memory cost continuously rather than only at pause boundaries.

## Hardware fit for M1 (8GB/16GB) and RTX 3070 (8GB VRAM)
- All of Silero VAD, TEN VAD, WebRTC VAD, LiveKit v1-mini, and Smart Turn v3 (int8, 8MB) are explicitly CPU-only-capable and sub-20MB, so they run trivially on an M1 8GB Mac or an RTX 3070 box without touching the GPU — confirmed per-model above.
- Smart Turn v2 (94.8M params, ~360-400MB) is heavier but still CPU-runnable; GPU (even the RTX 3070) accelerates it further but isn't required. [HF pipecat-ai/smart-turn-v2](https://huggingface.co/pipecat-ai/smart-turn-v2)
- LiveKit's full v1 audio turn detector appears designed primarily for LiveKit Cloud's optimized inference rather than confirmed-documented local self-hosting; v1-mini is the locally-runnable CPU variant — exact size/VRAM not found.
- Kyutai's semantic VAD is the outlier: it rides on a ~1B-parameter streaming STT, which is a non-trivial model to run continuously — on an 8GB M1 or 8GB RTX 3070 it would consume a meaningful fraction of available memory/VRAM, though no official VRAM/RAM figure was found in the fetched sources.

## Gaps
- No official parameter/size figures found for LiveKit's audio turn detector v1/v1-mini (only the deprecated text model's 396MB/Qwen2.5-0.5B size is documented).
- No isolated latency, parameter count, or memory footprint specific to Kyutai's semantic VAD component apart from its parent 1B-parameter STT model; the DSM arXiv preprint (2509.08753) likely has more detail but was not fully read (abstract only).
- No concrete VRAM figure found for running Kyutai's 1B STT + semantic VAD on an 8GB RTX 3070 — unconfirmed whether it fits alongside an STT and TTS model simultaneously.
- WebRTC VAD's own accuracy/false-positive numbers were not found (only that newer models claim to beat it); its exact binary/library size in KB and per-frame latency in ms were not found, only inferred as negligible from its DSP-only design.
- **Total-stack sizing** (STT + VAD + turn-detector + TTS together on an 8GB GPU) was not directly answered by sources — the pieces researched here (VAD: ~1-2MB; semantic turn detector: 8MB–400MB) are all small enough that they are very unlikely to be the constraint; the binding constraint is almost certainly the STT and TTS model sizes (covered by other researchers), not VAD/turn-detection. Based on the numbers found here, a VAD+turn-detector pair adds well under 500MB RAM/VRAM in the Smart Turn v3 / LiveKit v1-mini / Silero / TEN VAD case, leaving most of an 8GB RTX 3070's VRAM free for STT and TTS — but this composite claim was not itself verified against a vendor benchmark and should be treated as inference from the individual numbers above, not a sourced total.
