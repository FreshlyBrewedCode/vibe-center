# Prior Art: Voice-Based Control / Orchestration of AI Coding Agents

## Which OSS projects let you talk to Claude Code, OpenCode, Codex CLI, Gemini CLI, Aider etc. by voice?

### Takeaway
There is a large and fast-growing cluster of small, mostly single-maintainer OSS projects (dozens found, several new in the last ~2 months as of Oct 2026) that wrap an existing coding-agent CLI (overwhelmingly Claude Code) with STT/TTS to create a "talk to your agent" experience. Almost all of them drive a *single* existing session/harness rather than reimplementing the LLM loop, and almost all are young, low-star, single-maintainer repos — none has yet become a clearly dominant, heavily-starred standard. The most mature/most-starred is `mbailey/voicemode`.

### Cited Findings
- **mbailey/voicemode** — ~1.4k GitHub stars, MIT license, 2,300+ commits. MCP server exposing `mcp__voicemode__converse` and `mcp__voicemode__service` tools to any "MCP-capable agent" (Claude Code explicitly, plus others via MCP). STT/TTS can run fully local (Whisper.cpp + Kokoro) or via OpenAI cloud APIs; positioned as "natural voice conversations with Claude Code," hands-free, with silence detection and low latency. Works as both an MCP server and standalone CLI. — [GitHub](https://github.com/mbailey/voicemode)
- **hvieirapt/claude-voice-assistant** — "Talk to Claude Code by voice, fully local: hands-free assistant over all your sessions, permissions by voice, meeting minutes." Runs inside the Claude desktop app on macOS/Apple Silicon; only the Claude model call is cloud, STT/TTS run locally. Notably claims to operate "over all your sessions" (multi-session awareness), closer to a manager role than the single-session tools below. — [GitHub](https://github.com/hvieirapt/claude-voice-assistant)
- **caiovicentino/claude-call** — ~40 stars, MIT. Real phone-call-style voice I/O for a Claude Code session. STT: local whisper.cpp primary (~0.6s/utterance) with optional cloud (Groq, OpenAI, ElevenLabs, Google Chirp 2); TTS: free Microsoft edge-tts by default, optional premium (ElevenLabs, Cartesia, OpenAI, Rime, Deepgram). Architecture explicitly **single-session**: "the brain runs as a persistent daemon for the whole call," can resume the most recent session in a directory (`CALL_CONTINUE`), but has no multi-session switching/orchestration. Also ships a "hook mode" (`voice_hook.py`) that adds voice as a Claude Code Stop hook inside an existing interactive session instead of a separate headless process. — [GitHub](https://github.com/caiovicentino/claude-call)
- **dhuynh95/duck_talk** — ~27 stars, MIT. Real-time voice interface wrapping Claude Code without modifying the agent: a relay converts Claude's streaming token output to audio (Gemini TTS) and transcribes voice input via Gemini Live (STT), cloud-based, requires both `GEMINI_API_KEY` and `ANTHROPIC_API_KEY`. Supports interruption by saying "stop," streams sentence-by-sentence for ~1s time-to-first-audio, retains user transcription corrections, and has a "review mode" where instructions appear before execution so the user can edit/send/ignore. — [GitHub](https://github.com/dhuynh95/duck_talk)
- **dazauzai/voice-claude**, **yash-srivastava19/claude-voice**, **ethanplusai/jarvis**, **johnmatthewtennant/mcp-voice-hooks** — further single-maintainer "talk to Claude Code" variants (Windows/Mandarin support, local whisper.cpp+Kokoro, macOS "notify me when Claude needs me" assistant, and an MCP-hooks-based voice I/O plugin respectively); all discovered via search but not independently verified for star counts/activity beyond their README descriptions. — [Search results listing](https://github.com/search) (see individual repo pages: [voice-claude](https://github.com/dazauzai/voice-claude), [claude-voice](https://github.com/yash-srivastava19/claude-voice), [jarvis](https://github.com/ethanplusai/jarvis), [mcp-voice-hooks](https://github.com/johnmatthewtennant/mcp-voice-hooks))
- **abracadabra50/claude-code-voice-skill** — 172 stars, MIT, ~15 commits. Uses Vapi for telephony/webhook infrastructure, pluggable STT/TTS (OpenAI, ElevenLabs, Deepgram, PlayHT, Azure), Claude Opus 4.5 as the conversational LLM. A local server receives Vapi webhooks, injects project context (git status, files, todos) and "live tools" (read files, search code) into the call, and manages session state — explicitly architected so "Claude never directly handles session management," i.e. a thin orchestration layer sits between the phone call and the coding brain. Calls auto-save as markdown transcripts with summaries. This is the closest found example to a genuine phone-call-style voice *manager* pattern (though it manages context/tools for one call, not multiple concurrent coding-agent sessions). — [GitHub](https://github.com/abracadabra50/claude-code-voice-skill)
- Pipecat (pipecat-ai/pipecat) ships "Pipecat Skills for Claude Code" and a Pipecat MCP Server specifically to "talk to Claude Code via voice (including over WebRTC or phone call) from anywhere," i.e. Pipecat is being positioned as the telephony/voice-pipeline layer in front of Claude Code as the harness, rather than Pipecat replacing the agent. — [Pipecat docs: Build with a Coding Agent](https://docs.pipecat.ai/pipecat/get-started/ai-tools); [kwindla (Daily/Pipecat) announcement](https://x.com/kwindla/status/2022011497996816826)

### Inferences
- The space is dominated by hobbyist/single-maintainer wrappers around Claude Code specifically; coverage of OpenCode, Codex CLI, Gemini CLI, or Aider via *voice* directly is much thinner than coverage via ACP (see next section) — voice projects tend to target Claude Code first and only later/optionally generalize via MCP or ACP.
- "Single persistent session wrapped in voice I/O" is the dominant pattern; genuine multi-session/multi-agent voice *management* (the "voice manager agent" concept) is rare and mostly found at the edges (claude-voice-assistant's "over all your sessions" claim, the Pipecat MCP server's "from anywhere" framing, and qwen-audio-agent's multi-agent ACP support below).

### Gaps
- Could not verify last-commit dates precisely for voicemode, duck_talk, claude-call (GitHub's commit timestamps weren't surfaced in fetched content); treat all of these as needing a freshness check at use time.
- No OSS voice wrapper specifically targeting Aider was found in this search pass.

## Are there projects combining voice with ACP? What's the state of ACP adapters?

### Takeaway
ACP (agentclientprotocol.com) has real adapter coverage for Claude Code, OpenCode, Codex and Gemini CLI, and at least one purpose-built voice-over-ACP project (qwen-audio-agent) plus an Android voice client (VACP) exist — this is the most promising existing substrate for a harness-agnostic voice manager, since ACP already standardizes session/turn/permission semantics across agents.

### Cited Findings
- Claude Code exposes itself over ACP via the official `@agentclientprotocol/claude-agent-acp` adapter, used by ACP clients like Zed. — [WebSearch synthesis citing agentclientprotocol.com](https://agentclientprotocol.com/get-started/clients)
- **qwen-audio-agent** (also mirrored as QwenAudio/qwen-audio-agent, Apache-2.0) is a "realtime voice runtime that keeps Agents talking, working, and present" — a full-duplex voice frontend over ACP with on-device wake word ("你好千问" via sherpa-onnx, no cloud round-trip) and barge-in (truncates agent audio output and starts a new input turn the instant the user speaks). It explicitly connects to **Claude Code, Codex, OpenCode, Kimi CLI and other agents over ACP**, making it the clearest existing example of a harness-agnostic voice-over-ACP project. — [GitHub](https://github.com/QwenAudio/qwen-audio-agent); [betterstack writeup](https://betterstack.com/community/guides/ai/qwen-audio-agent/); [QwenLM/qwen-code ecosystem PR](https://github.com/QwenLM/qwen-code/pull/8630)
- **VACP** (Android app, "Voice Control for OpenCode") lets users talk to ACP-compatible agents (OpenCode, KiloCode, "any ACP-compatible agent over TCP") and explicitly supports **connecting to multiple ACP-compatible agents and switching between them while managing different development sessions** — i.e., closer to multi-session voice management than most Claude-Code-specific wrappers. — [Google Play listing](https://play.google.com/store/apps/details?id=com.intellexie.vacp&hl=en_AU)
- Other generic ACP clients exist that are not voice-specific but establish the adapter ecosystem a voice manager could sit on top of: `formulahendry/vscode-acp` and `formulahendry/acp-ui` (connect to Claude, Codex, Copilot, Qwen, Gemini, OpenCode, Kiro, etc.), `kodizm/acp` ("One ACP surface, three CLI backends: Claude Code, Codex, opencode — drive them without backend-specific orchestrator code"), `SammyLin/opencode-claude-acp` (call Claude Code from OpenCode over ACP with resumable named sessions), and `VACInc/acpx` (headless CLI client for stateful ACP sessions — persistent sessions, parallel named workstreams, prompt queueing when a turn is already running). — [vscode-acp](https://github.com/formulahendry/vscode-acp); [acp-ui](https://github.com/formulahendry/acp-ui); [kodizm/acp](https://github.com/kodizm/acp); [opencode-claude-acp](https://github.com/SammyLin/opencode-claude-acp); [acpx](https://github.com/VACInc/acpx)
- There is early experimentation with ACP-based *orchestrators* (task trees, mcp-delegate, control servers) in `0xbasinas/acportal` (PR #45), suggesting the community is actively prototyping the manager-of-agents pattern on top of ACP, though this is explicitly experimental/in development. — [GitHub PR](https://github.com/0xbasinas/acportal/pull/45)

### Inferences
- ACP's standardized session lifecycle (create session, stream turns, abort, permission requests) is a better integration point for a voice *manager* than raw per-harness APIs, because one voice/orchestration layer (like qwen-audio-agent or VACP) can already drive Claude Code, Codex, OpenCode, Gemini CLI etc. interchangeably.
- acpx's "persistent sessions... parallel named workstreams... queue follow-up prompts when a turn is already running" is directly relevant primitive for a voice manager juggling multiple worker threads.

### Gaps
- Could not confirm current ACP adapter status specifically for Gemini CLI and Codex (official vs. community-maintained, and how complete); the search surfaced client-side support claims but not first-party adapter repos for Gemini/Codex analogous to `claude-agent-acp`.
- No GitHub star/activity data was gathered for qwen-audio-agent, VACP, or acpx — flag as needing a freshness/traction check.

## How do the Claude Agent SDK and OpenCode server/SDK support streaming, interruption, and session management relevant to a voice loop?

### Takeaway
Both the Claude Agent SDK (TS/Python) and the OpenCode HTTP server expose exactly the primitives a voice loop needs — long-lived sessions, token/event streaming, mid-turn interruption, and queued follow-up prompts — making either viable as "the brain" behind a voice manager, or as a managed worker that the voice manager talks to over HTTP/SSE or SDK calls.

### Cited Findings
- Claude Agent SDK: "Streaming input mode is the preferred way to use the Claude Agent SDK... allows the agent to operate as a long lived process that takes in user input, handles interruptions, surfaces permission requests, and handles session management." Single-message mode is explicitly the wrong fit for interactive/interruptible use (recommended only for one-shot/Lambda/non-interactive scripts). — [Streaming Input docs](https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode)
- TypeScript SDK: `interrupt()` method interrupts an in-flight query, only available in streaming input mode. Python SDK: plain `query()` function does **not** support interrupts; `ClaudeSDKClient` does support interrupts, again only in streaming input mode. — [Agent SDK TypeScript reference](https://code.claude.com/docs/en/agent-sdk/typescript); [Agent SDK Python reference](https://platform.claude.com/docs/en/agent-sdk/python)
- OpenCode exposes a headless HTTP server (`opencode serve`) with an OpenAPI surface: `POST /session` to create a session, `GET /event` as a global Server-Sent-Events stream carrying incremental message parts/tool activity/permission requests, `POST /session/{sessionID}/prompt_async` to submit prompts without blocking, `GET /session/{sessionID}/message` to read messages, and `POST /session/{sessionID}/abort` to cancel in-flight work (returns a boolean). Typical workflow: create session → open `/event` SSE stream → post prompt → observe agent work on the SSE stream. — [opencode.ai Server docs](https://opencode.ai/docs/server/); community confirmation of `/session/:id/abort` ([GitHub issue discussion](https://github.com/anomalyco/opencode/issues/13416))
- A known rough edge: "SDK SSE stream can deliver events after cancellation" — an open OpenCode issue indicating abort/cancel races in the event stream that a voice manager relying on OpenCode's abort-then-silence semantics should account for. — [GitHub issue #53965](https://github.com/anomalyco/opencode/issues/53965)

### Inferences
- Architecturally, a voice manager has two integration choices per worker: (a) embed the Claude Agent SDK directly as the "brain" with full interrupt support via `ClaudeSDKClient`/TS `interrupt()`, or (b) drive external OpenCode sessions over HTTP/SSE using `prompt_async` + `/event` + `/abort` as a language/process-agnostic remote-control surface — the latter maps naturally onto "manage other agents/threads" rather than "be the agent."
- The abort-after-cancel SSE race in OpenCode is a concrete thing to design around (e.g., client-side tagging of post-abort events) if OpenCode sessions are used as managed workers behind a voice interface.

### Gaps
- Did not find OpenCode SDK (JS/TS client library) specifics beyond the raw HTTP API — e.g., whether there's a typed streaming client wrapping `/event`, and whether OpenCode supports partial/token-level streaming versus only part-level increments.
- Did not verify whether Claude Agent SDK's interrupt is a hard-stop or a graceful "finish current tool call" interrupt — relevant for barge-in latency.

## Agent-manager / orchestration tools (Claude Squad, Vibe Kanban, Conductor, Crystal, Omnara, Happy Coder) — which have voice features?

### Takeaway
Among the well-known multi-agent orchestration tools, **Omnara** and **Happy Coder (slopus/happy)** are the two with real, shipped voice features, both aimed at mobile/phone-first control of Claude Code and Codex; Claude Squad, Vibe Kanban, Conductor, and Crystal are terminal/desktop-oriented session managers with no voice feature found. This is the most direct prior art for "a voice interface whose job is managing coding-agent sessions rather than coding."

### Cited Findings
- **Omnara** (YC S25, founded 2025) — lets users monitor, steer, and approve live Claude Code/Codex sessions running on a laptop, from iOS/Android/web/Apple Watch. Ships a "Voice Coding Mode" for natural two-way voice brainstorming/iteration, explicitly pitched for "coding while commuting or walking"; sessions migrate to the cloud when the laptop goes offline so the phone/voice interface keeps working. — [Launch HN](https://app.daily.dev/posts/launch-hn-omnara-yc-s25-run-claude-code-and-codex-from-anywhere-b3n2icy7y); [App Store listing](https://apps.apple.com/us/app/omnara-claude-codex-mobile/id6748426727)
- **Happy Coder / slopus/happy** — free, fully open-source mobile+web client that lets users "spawn, view, and control multiple Claude Code [and Codex] AI coding agent sessions on any device... by syncing them in real time," with realtime voice input and end-to-end encryption. Architecture: CLI (`happy`, npm package, formerly `happy-coder`) running on the dev machine + an encrypted relay server + mobile apps (iOS/Android) + web UI. The original CLI is now in "maintenance mode," with new features shipping in a Happy desktop app instead. This is the clearest example of a tool whose job is explicitly multi-session orchestration (not single-session wrapping) with voice as one of several input modes. — [slopus/happy](https://github.com/slopus/happy); [Happy docs: voice coding rationale](https://happy.engineering/docs/features/voice-coding-with-claude-code/); [Happy docs: features](https://happy.engineering/docs/features/)
- **Claude Squad** — terminal manager using tmux + git worktrees to run several agents at once (agent-agnostic: also drives Codex, Aider); no voice feature found in search. — [Munder Difflin orchestrator comparison](https://munderdiffl.in/blog/claude-code-orchestration-tools-compared/)
- **Vibe Kanban** — open-source, locally run, browser-UI kanban board where each task goes to an agent in its own git worktree, supports ~10 agents; project is "sunsetting" as a commercial product but continuing as community-maintained OSS. No voice feature found. — [same comparison](https://munderdiffl.in/blog/best-claude-code-multi-agent-tools/); [vibekanban.com](https://www.vibekanban.com/)
- **Conductor** — polished Mac app, isolated git-worktree workspace per agent (Claude Code + Codex), diff viewer/PR flow, optional cloud workspaces on paid plans. No voice feature found.
- **Crystal** — deprecated by its maker in February 2026 and replaced by **Nimbalyst**, an MIT-licensed visual workspace for Claude Code/Codex; no voice feature found for either Crystal or its successor in this search pass. — [Munder Difflin / Nimbalyst blog](https://nimbalyst.com/blog/best-agent-management-tools-2026/)

### Inferences
- The two orchestration tools that *did* add voice (Omnara, Happy) both did so specifically to solve the "control your coding agent while away from a keyboard" problem (commuting, phone-first), not to replace the manual session-management UI — i.e., voice is layered on top of an already-built multi-session control plane, which matches the "voice manager agent drives an existing harness" framing in the research objective.
- None of the surveyed tools appear to use voice as the *primary* interface with an LLM acting as an active dispatcher/manager deciding which session to route a spoken request to — the voice features found are closer to "dictate to a selected session" than to "delegate across sessions by voice," suggesting real whitespace for the "voice manager agent" concept as distinct from existing OSS.

### Gaps
- Could not verify current GitHub star counts, license, or last-commit dates for Omnara (appears to be a product/app, possibly not primarily open-source — could not confirm OSS license) or for slopus/happy specifically (only derivative forks' metadata was visible, not the upstream repo's own stats).
- No information found on whether Omnara's voice mode supports interrupting/barge-in mid-response, or whether it's push-to-talk only.

## Write-ups from people who built voice control for coding agents — lessons learned

### Takeaway
General realtime-voice-agent engineering literature (not all specific to coding agents) converges on: optimize time-to-first-audio over total latency, treat tool/function calls as the main latency cliff (since many STT/LLM providers must see a complete response before firing a tool call), use UDP/WebRTC rather than WebSocket for media transport, and build in explicit barge-in / voice-activity-detection rather than push-to-talk for a "real conversation" feel. Coding-agent-specific write-ups are thinner than generic voice-AI write-ups, but the coding-specific tools reviewed above converge on the same local-first, interrupt-first, streaming-sentence-by-sentence design.

### Cited Findings
- "The transport layer matters more than model choice... For voice AI, WebSockets can't be part of the equation. If you're building something users will actually talk to, you need UDP or WebRTC for the media transport." — [rnikhil.com, "How to optimise latency for voice agents"](https://rnikhil.com/2025/05/18/how-to-reduce-latency-voice-agents)
- "You cannot use text streaming when doing function calling. The model needs to see the complete response to know it should trigger a function... Tool calls are the latency cliff, not the model. A single round of tool calling can roughly double perceived response time." — [rnikhil.com](https://rnikhil.com/2025/05/18/how-to-reduce-latency-voice-agents) — directly relevant to a voice manager agent, since "delegate to an agent / check on a thread" is itself a tool call.
- "A latency budget of roughly 800 milliseconds to first audible response is needed, along with voice activity detection, end-of-turn detection, barge-in that stops the agent the instant a user speaks, and tool calls that must not leave dead air." — [braiviq.com playbook](https://www.braiviq.com/playbook/building-real-time-voice-agents-code-2026-speech-to-speech-vs-cascaded-latency-turn-detection-barge-in)
- "Optimize the first token, not the total... Once audio starts playing the caller is occupied, so time-to-first-audio dominates perceived speed almost entirely." — [Agora, "10 Lessons Learned Building Voice AI Agents"](https://www.agora.io/en/blog/lessons-learned-building-voice-ai-agents/)
- Coding-agent-specific echoes of the same principles appear directly in the tool READMEs surveyed above: duck_talk streams TTS sentence-by-sentence for "~1s to first audio" and supports saying "stop" to interrupt mid-response ([GitHub](https://github.com/dhuynh95/duck_talk)); claude-call keeps "the brain" as a persistent daemon for the whole call so "context stays cached, replies stream as it talks" ([GitHub](https://github.com/caiovicentino/claude-call)); qwen-audio-agent's barge-in "truncates the agent's audio output stream and starts a new input turn" the instant speech is detected, and runs a non-blocking voice-agent layer ("never blocks on work") so continuous audio capture/transcription/synthesis don't stall on agent work ([betterstack.com](https://betterstack.com/community/guides/ai/qwen-audio-agent/)).

### Inferences
- For a voice *manager* agent specifically (as opposed to a voice *coder*), the "tool calls are the latency cliff" lesson is amplified: every spoken instruction to the manager likely requires at least one dispatch/status-check tool call (e.g., "what's thread 3 doing") before any audio can be produced, so the manager's own tool-call latency (not the worker agent's) sets the perceived responsiveness floor — arguing for either a fast/cheap routing model in front of the full manager LLM, or pre-fetched/cached thread-status state the manager can speak from immediately.
- No coding-agent-specific publication was found that discusses the specific problem of *spoken status summarization across multiple concurrent async agent threads* (vs. a single foreground session) — this appears to be genuinely underexplored prior art, reinforcing that a "voice manager of agents" concept is still a gap in the current OSS landscape rather than a solved, well-documented problem.

### Gaps
- Found no first-person blog/HN post specifically titled around "I built voice control for Claude Code / OpenCode and here's what I learned" with concrete before/after latency numbers for a *coding* (vs. generic customer-support-style) voice agent; the closest artifacts are the tool READMEs themselves (treated as primary-source engineering notes above) rather than reflective write-ups.
- No data found on real-world user feedback/adoption friction for any of the voice-coding-agent tools (e.g., accuracy of voice-driven code edits, frustration with STT errors on code/identifier names).
