# Local STT, VAD, and Turn Detection for a Real-Time Voice Agent

Research current as of 2026-10-29. Target hardware: (a) Apple M1 Mac, 8GB and 16GB unified memory; (b) Linux/Windows PC with NVIDIA RTX 3070 (8GB VRAM). Note: much of the fast-moving coverage comes from aggregator/benchmark blogs (northflank, localaimaster, promptquorum, gigagpu, vexascribe, whisperNotes, etc.) rather than primary vendor sources; these are flagged explicitly below and should be treated as secondary/lower-confidence unless corroborated by a primary source (official repo, model card, vendor blog).

## Which local STT gives the lowest end-of-utterance latency on each target, and is streaming or VAD-chunked batch better?

### Takeaway
On both target platforms, true low-latency "time-to-final-transcript-after-end-of-speech" is best achieved either by a genuinely streaming model (Kyutai STT, sherpa-onnx streaming Zipformer) or by a very fast batch model run on a short VAD-cut segment (NVIDIA Parakeet-TDT on the RTX 3070; whisper.cpp/WhisperKit/MLX-Whisper with CoreML/Metal/ANE on the M1). For the RTX 3070, Parakeet-TDT 0.6B (via sherpa-onnx/onnx-asr or NeMo) is the standout for both speed and accuracy; for Apple Silicon, WhisperKit/whisper.cpp-CoreML and parakeet-mlx are the fastest options. Chunked/batch-on-VAD-segment is simpler to build and, given how fast these small/medium models now run, is likely "fast enough" for a conversational agent (sub-300ms) without needing true incremental streaming — except where sub-200ms responsiveness or long dictation-while-speaking display is required, in which case Kyutai STT's genuine streaming with partial text is the only true-streaming local option.

### Cited Findings
- NVIDIA Parakeet-TDT-0.6B-v2 tops the Hugging Face Open ASR Leaderboard at ~6.05% WER and reports an RTFx of 3380 at batch size 128 on the leaderboard (i.e., able to process ~3380x real time in batch on NVIDIA GPU hardware), ahead of Whisper large-v3 (~7.44% WER) and large-v3-turbo (~7.7–7.83% WER) — [Hugging Face model card](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v2); aggregated in [Northflank STT benchmark roundup](https://northflank.com/blog/best-open-source-speech-to-text-stt-model-in-2026-benchmarks) (secondary, cross-check only).
- Parakeet-TDT-0.6B-v2 is a 600M-parameter FastConformer-TDT model trained with full attention, able to transcribe up to 24 minutes of audio in a single pass — [Hugging Face model card](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v2).
- Community/aggregator benchmark reports faster-whisper large-v3-turbo at ~19.2s (fp16, 2537MB peak mem) or ~19.6s (int8, 1545MB peak mem) to transcribe a fixed audio sample on an NVIDIA GPU, and that large-v2/v3 fp16 beam-5 uses ~4525MB VRAM, well within an 8GB RTX 3070's budget — [GIGAGPU Whisper vs Faster-Whisper](https://gigagpu.com/whisper-vs-faster-whisper-speed/) (secondary/aggregator; exact GPU model for these specific numbers not confirmed in the source, treat as directional only).
- Kyutai STT uses a "delayed streams modeling" architecture that processes audio and text as parallel streams with a small fixed delay rather than waiting for silence: the 1B English/French model (`kyutai/stt-1b-en_fr`) has a ~0.5s delay, and the 2.6B English model (`kyutai/stt-2.6b-en`) has a ~2.5s delay — [GitHub kyutai-labs/delayed-streams-modeling](https://github.com/kyutai-labs/delayed-streams-modeling), [Kyutai STT page](https://kyutai.org/stt/).
- Kyutai's "flush trick" processes buffered audio at roughly 4x real-time once speech ends, so with the 1B model's 500ms streaming delay, the last words of an utterance can arrive roughly 125ms after the true end of speech — cited via community deep-dive, not a primary Kyutai doc: [Medium: Unmute deep dive](https://medium.com/@kauxhik77/unmute-giving-voice-to-ai-a-deep-dive-into-kyutais-framework-6d8f83bc9531) (secondary; treat the specific "125ms" figure as unconfirmed/approximate pending a primary source).
- On an H100, Kyutai's delayed-streams architecture can run ~400 real-time audio streams simultaneously in server mode, a throughput figure rather than a single-stream latency figure — [GitHub kyutai-labs/delayed-streams-modeling](https://github.com/kyutai-labs/delayed-streams-modeling).
- whisper.cpp on an M1 with Metal acceleration runs the `small` model at ~12x real-time and the `medium` model at ~5x real-time; with CoreML acceleration specifically, community benchmarks report `small` at RTF 0.03 (≈33x real-time) and `medium` at RTF 0.08 (≈12.5x real-time) — [promptquorum Apple Silicon Whisper benchmark](https://www.promptquorum.com/local-llms/apple-silicon-whisper-metal-benchmark) (aggregator; numbers not independently verified against the whisper.cpp repo's own benchmark tables).
- WhisperKit (Argmax) reports ~2.2% WER using an optimized large-v3-turbo variant on the Apple Neural Engine while running at real-time streaming latency, and WhisperKit's per-word latency in Argmax's own comparison was ~0.45s mean, tied with "Fireworks" — [Argmax WhisperKit Benchmarks on Hugging Face](https://github.com/argmaxinc/argmax-oss-swift/discussions/243), [Argmax blog: Apple SpeechAnalyzer and Argmax WhisperKit](https://www.argmaxinc.com/blog/apple-and-argmax). Argmax publishes continuously updated benchmarks on a Hugging Face Space (not independently re-verified in this pass).
- lightning-whisper-mlx claims to be ~10x faster than whisper.cpp and ~4x faster than plain MLX Whisper via batched decoding, quantization, and greedy-only decoding, with one community test showing 15.3s to transcribe a sample (36.4x realtime) vs. mlx-whisper's 18.7s (29.7x realtime) — [Lightning Whisper MLX project page](https://mustafaaljadery.github.io/lightning-whisper-mlx/) (primary repo claim; the specific RTF numbers are from an unverified community benchmark).
- parakeet-mlx (community MLX port of NVIDIA's Parakeet for Apple Silicon) supports real-time streaming with the 0.6B model requiring a minimum of ~2GB of unified memory, making it viable even on the 8GB M1 — [GitHub senstella/parakeet-mlx](https://github.com/senstella/parakeet-mlx) (community project, not an NVIDIA-maintained repo).
- Open ASR Leaderboard paper confirms it is intended as the reproducible, transparent reference for multilingual/long-form ASR evaluation — [Open ASR Leaderboard paper (arXiv:2510.06961)](https://arxiv.org/pdf/2510.06961).

### Inferences
- For the RTX 3070 (8GB VRAM), Parakeet-TDT 0.6B is likely the single best latency/accuracy tradeoff for English: it is both more accurate (6.05% WER) and dramatically faster in batch/offline RTF terms than any Whisper variant, and at 600M parameters it comfortably fits in 8GB VRAM alongside a VAD model and a small-to-medium TTS model. Since Parakeet-TDT itself is not natively streaming (it is a FastConformer-TDT offline/chunked model), the practical architecture on this hardware is "VAD segments speech → fast batch ASR pass," not token-by-token streaming — which is fine given RTF is so favorable that the ASR pass itself adds only tens of milliseconds after VAD fires.
- For Apple Silicon (M1, 8GB/16GB), WhisperKit (CoreML/ANE) and parakeet-mlx are the most promising for low end-of-utterance latency given their reported near-real-time or faster processing and small memory footprint; whisper.cpp with Metal/CoreML is a safe, mature fallback with well-documented RTFs. On 8GB M1 specifically, memory pressure makes smaller models (whisper small/medium, Parakeet 0.6B, Moonshine) much safer than whisper large-v3; 16GB gives comfortable headroom to run large-v3-turbo or Parakeet/Canary alongside other agent components.
- Kyutai STT is the only candidate offering genuine incremental streaming transcription with sub-second committed latency by design, which matters mainly if the agent wants to show live partial transcripts while the user is still talking, or needs sub-200ms reaction once speech plausibly ends; for most "wait for pause, then respond" voice agents, the VAD + fast-batch-ASR approach is simpler and likely has comparable practical latency to Kyutai's streaming approach, especially once VAD/turn-detection overhead is counted on both sides.

### Gaps
- No RTX-3070-specific (as opposed to generic "an NVIDIA GPU" or newer-GPU) benchmark numbers were found for faster-whisper, Parakeet, or Canary; most community benchmarks used unspecified or different GPUs (e.g., L40S, A100, T4, 4090). All GPU latency/RTF numbers above should be treated as directional for an 8GB Ampere-class card, not confirmed for the 3070 itself.
- No concrete milliseconds-after-end-of-speech figure was found for WhisperKit, whisper.cpp, or Parakeet-TDT in the VAD-chunked-batch paradigm (i.e., "VAD fires at time T, final transcript token appears at T+Xms"); the RTF-style figures found describe steady-state throughput, not this specific end-to-end latency metric.
- No primary-source, first-party benchmark table from Argmax/WhisperKit, NVIDIA/Parakeet, or Kyutai measuring this project's exact "time-to-final-transcript after end-of-speech" metric was retrieved in this pass; what's cited above is the closest available proxy data (RTF/throughput, or streaming-delay-by-design figures).

## How much VRAM/RAM do STT + VAD + turn-detection models need together, and does that leave room for TTS on the RTX 3070's 8GB?

### Takeaway
On the RTX 3070, a practical stack of Parakeet-TDT-0.6B or faster-whisper large-v3-turbo (int8) for STT (roughly 1.5–4.5GB VRAM), Silero VAD or TEN VAD (negligible, sub-100MB, largely CPU-friendly), and a semantic turn detector such as Smart Turn v2/v3 or LiveKit's turn-detector (hundreds of MB, GPU-optional) together use well under half of the 8GB budget, leaving several GB free for a lightweight local TTS model (Kokoro ~2–3GB VRAM, Piper ~0.3GB). On the M1, the relevant constraint is unified memory shared with the OS and any LLM; an 8GB M1 is tight once you add a conversational LLM into the mix, while 16GB gives comfortable headroom for STT+VAD+turn+TTS plus a small-to-mid LLM.

### Cited Findings
- Silero VAD is tiny: ~309K parameters, ~1.2MB on disk (JIT ~2MB, ONNX ~2MB), processes a 30+ms audio chunk in under 1ms on a single CPU thread, with <5% CPU usage on a single core — [GitHub snakers4/silero-vad](https://github.com/snakers4/silero-vad), [FluidInference silero-vad-coreml README](https://huggingface.co/FluidInference/silero-vad-coreml/blob/4f5583ac422319f58fc3414becb5039d2f25092b/README.md).
- TEN VAD reports an average inference time of ~0.17ms per frame and is claimed to be ~48% faster than Silero VAD with a lower false-positive rate, per TEN-framework's own benchmark page — [TEN VAD docs](https://theten.ai/docs/ten_vad), [Agora blog on TEN VAD](https://www.agora.io/en/blog/making-voice-ai-agents-more-human-with-ten-vad-and-turn-detection/) (TEN's own comparison numbers; independent third-party verification not found).
- Pipecat Smart Turn v2 is a 94.8M-parameter model, 360MB as safetensors (6x smaller than Smart Turn v1's 2.3GB), taking ~12ms to analyze 8s of audio on an NVIDIA L40S, ~19ms on an A100, ~75ms on a T4 (g4dn.xlarge), and ~410ms on a 16-core x86_64 CPU — [Hugging Face pipecat-ai/smart-turn-v2](https://huggingface.co/pipecat-ai/smart-turn-v2), [Daily blog: Smart Turn v2](https://www.daily.co/blog/smart-turn-v2-faster-inference-and-13-new-languages-for-voice-ai/).
- Smart Turn v3 is reported by Daily/Pipecat as achieving CPU inference in ~12ms, is ~50x smaller than earlier versions, supports 23 languages (including German and English), is BSD-2-Clause licensed, and ships open weights, open training data, and open training code — [Daily blog: Announcing Smart Turn v3](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/).
- LiveKit's turn-detector model is fine-tuned from Qwen2.5-0.5B-Instruct (both variants), explicitly chosen to allow low-latency CPU inference, and the v1 "mini" variant is optimized specifically for fast CPU inference; v1 fuses semantic (transcript) and acoustic (raw audio) signals and covers 14 languages — [LiveKit blog: Solving end-of-turn detection v1.0](https://livekit.com/blog/solving-end-of-turn-detection), [Hugging Face livekit/turn-detector](https://huggingface.co/livekit/turn-detector). At 0.5B parameters this is meaningfully larger than Smart Turn (94.8M) or Silero VAD, implying higher memory/compute cost even though it still targets CPU.
- Kokoro-82M TTS needs roughly 2–3GB VRAM (or can run CPU-only) and is Apache-2.0 licensed with 54 voices across 8 languages — [localaimaster TTS VRAM guide](https://localaimaster.com/blog/voice-ai-vram-requirements-by-gpu) (aggregator, cross-check against Kokoro's own Hugging Face model card recommended before relying on exact VRAM figure).
- Piper TTS needs only ~0.3GB VRAM/RAM, ships ~300MB models, runs ~96x real-time even on CPU, and supports 47 languages with 900+ voices, making it a near-free addition to any budget — [localaimaster TTS VRAM guide](https://localaimaster.com/blog/voice-ai-vram-requirements-by-gpu) (aggregator; cross-check against Piper's own repo recommended).
- A generic "voice agent stack" example cited by an aggregator pairs faster-whisper (~3–4GB), a 7B LLM at Q4 (~6–8GB), and Kokoro/MeloTTS (~1–2GB), stating this combination needs a 24GB card (e.g., RTX 3090) to fit comfortably — implying that on an 8GB RTX 3070, a full LLM + STT + TTS + VAD/turn stack would need careful model-size trimming (e.g., smaller/quantized LLM, int8 STT) — [GIGAGPU/localaimaster voice AI VRAM guides](https://gigagpu.com/best-gpu-for-tts-voice-ai/) (aggregator).

### Inferences
- STT, VAD, and turn-detection together are cheap relative to an 8GB VRAM budget: Parakeet-TDT 0.6B (int8/fp16, likely 1–2.5GB), Silero/TEN VAD (tens of MB), and Smart Turn v2/v3 or LiveKit turn-detector (a few hundred MB to ~1GB for the 0.5B LiveKit model) sum to roughly 2–4GB, leaving 4–6GB free on an RTX 3070 — comfortably enough for Kokoro or Piper TTS, and potentially a small quantized LLM if the STT model chosen is on the smaller/quantized end.
- The binding constraint on an 8GB GPU is much more likely to be the conversational LLM than the STT+VAD+turn+TTS voice stack itself; if the LLM is also local and GPU-resident, careful quantization (Q4 or lower on a 7B-class model, or a smaller model) will be necessary to leave room for the voice components.
- On the 8GB M1, unified memory is shared across OS, STT, VAD, turn-detector, TTS, and any LLM — meaning the "headroom" calculus is less forgiving than on a discrete 8GB GPU where the OS doesn't compete for the same pool. The 16GB M1 configuration removes most of this pressure for the voice stack alone.

### Gaps
- No official VRAM figure was found directly from NVIDIA's own Parakeet-TDT or Canary model cards (the figures compiled above for Whisper and TTS come from secondary aggregator posts, not confirmed against primary sources in this pass).
- No concrete combined "STT+VAD+turn+TTS" memory measurement from a single integrated benchmark (e.g., an actual Pipecat or LiveKit reference deployment with measured peak VRAM) was found; the sum used above is inferred by adding independently-sourced per-component figures, which may undercount runtime overhead (CUDA context, activation buffers, model-loading duplication) in a real multi-model pipeline.
- No Apple-Silicon-specific combined memory measurement for a full STT+VAD+turn-detector+TTS pipeline was found; M1 8GB vs 16GB guidance above is an inference, not a cited measurement.

## How accurate are these models on technical/coding vocabulary (repo names, CLI commands), and what custom-vocabulary/hotword support exists?

### Takeaway
No model in this list has published WER figures specific to technical/coding vocabulary; accuracy on jargon, repo names, and CLI commands must be inferred from general-domain WER plus the presence (or absence) of a custom-vocabulary/biasing mechanism. Whisper-family tools (via faster-whisper) have the most mature and flexible biasing support (`initial_prompt` and the newer `hotwords` parameter); Vosk and sherpa-onnx (Kaldi/k2-lineage tools) have long-standing grammar/context-biasing support designed exactly for this kind of controlled-vocabulary boosting; Parakeet/Canary and Kyutai's ecosystem were not found to document an equivalent hotword/biasing feature in this pass.
### Cited Findings
- faster-whisper supports both `initial_prompt` (a soft decoding bias that only reliably affects the first ~30s window/223-token context before falling out of context) and a newer `hotwords` parameter (re-prepended to every decoding window, so it persists across the whole audio, introduced in faster-whisper 1.0+, with the list-of-strings format required from 1.0+ and the "every window" behavior confirmed as of 1.2.1) — [GitHub SYSTRAN/faster-whisper discussion threads](https://github.com/ivrit-ai/ivrit-py/issues/26), [theneuralbase faster-whisper hotwords docs](https://theneuralbase.com/faster-whisper/learn/intermediate/hotwords-parameter-v1-0/), [theneuralbase initial_prompt docs](https://theneuralbase.com/faster-whisper/learn/intermediate/initial-prompt-for-domain-vocabulary/) (community/third-party documentation, not the official faster-whisper README, but consistent with the GitHub issue discussion from the ivrit-ai maintainers).
- The hotwords boost in faster-whisper is applied probabilistically during beam search (a bias, not a hard constraint): if the acoustic confidence for a competing token is very high, hotwords may have no effect even for a phonetically similar target word — [theneuralbase faster-whisper hotwords docs](https://theneuralbase.com/faster-whisper/learn/intermediate/hotwords-parameter-v1-0/) (secondary doc summarizing observed beam-search behavior).
- Vosk explicitly supports streaming partial/final results and documents a language-model-adaptation workflow for custom vocabularies — [Vosk LM adaptation docs](https://alphacephei.com/vosk/lm) (primary vendor doc).
- sherpa-onnx (k2-fsa) is a general ASR/TTS/VAD toolkit with broad model support (including streaming Zipformer); it is Kaldi/k2-lineage and thus inherits that ecosystem's traditions of context-biasing/hotword lists for transducer models, though no specific benchmark of hotword effectiveness for "technical vocabulary" was found in this pass — [GitHub k2-fsa/sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) (feature inferred from ecosystem documentation, not independently confirmed with a hotword-specific doc page in this pass — treat as a gap below).

### Inferences
- For a voice agent whose users will say repo names, CLI flags, and command syntax, faster-whisper's `hotwords` parameter (or Vosk's vocabulary adaptation) is likely the most practical lever available today among the candidates researched, since it directly targets this use case and is documented with concrete usage semantics.
- Parakeet-TDT's higher baseline WER-leaderboard accuracy (6.05% vs. Whisper large-v3's 7.44%) may partially compensate for the lack of a documented hotword mechanism on general technical speech, but for genuinely out-of-distribution tokens (uncommon repo names, invented CLI subcommands) a biasing mechanism is likely to matter more than small baseline WER differences — this is an inference, not something directly measured in any source found.

### Gaps
- No source was found reporting WER specifically on a technical/coding-vocabulary test set (e.g., spoken repo names, shell commands) for any of the candidates; this entire question is answered by inference from general WER + biasing-feature availability, not direct measurement.
- No documentation was found confirming or denying a hotword/custom-vocabulary mechanism for NVIDIA Parakeet-TDT, Canary, Kyutai STT, Moonshine, or WhisperKit/MLX-Whisper specifically (as opposed to faster-whisper/CTranslate2's Python-level `hotwords`/`initial_prompt`, which runs on the same underlying Whisper architecture but as a separate implementation). This is a meaningful gap for choosing a technical-vocabulary-friendly stack.
- sherpa-onnx's own hotword/context-biasing feature was not directly verified against its official docs in this pass (time-constrained); its presence is inferred from the Kaldi/k2 ecosystem lineage rather than confirmed in sherpa-onnx's own documentation.

## How do semantic turn detectors reduce false interruptions vs. pure silence-based VAD, and at what latency/hardware cost?

### Takeaway
Semantic turn detectors (Smart Turn v2/v3, LiveKit's turn-detector, Kyutai's semantic VAD) look at linguistic completeness (and sometimes prosody) rather than only acoustic silence, which lets them avoid interrupting a user who pauses mid-thought — a known failure mode of pure silence-based VAD (Silero, WebRTC VAD, TEN VAD). The added hardware/latency cost is now very small: Smart Turn v3 runs in ~12ms on CPU, and LiveKit's turn-detector is explicitly designed for CPU inference, so layering semantic turn detection on top of a VAD (which fires first to find candidate pause boundaries) adds single-digit-to-low-double-digit milliseconds of extra latency on modern hardware, not a meaningful new hardware requirement.

### Cited Findings
- Kyutai's semantic VAD (used in their "Unmute" demo) evaluates the actual linguistic syntax and intonation to predict the probability a speaker has finished a thought, specifically to avoid interrupting someone who is just pausing mid-sentence rather than done talking — [Kyutai on X](https://x.com/kyutai_labs/status/1925840425052426634), echoed in [kyutai/stt-2.6b-en discussion](https://huggingface.co/kyutai/stt-2.6b-en/discussions/5).
- Kyutai's semantic VAD is available in their Rust server implementation but not yet in all other implementations, and is only implemented on the smaller 1B model (not the larger 2.6B English model) as of this research — [Hugging Face kyutai/stt-2.6b-en discussion #5](https://huggingface.co/kyutai/stt-2.6b-en/discussions/5) (community discussion thread on the model's own HF page, closer to primary than a blog aggregator but still a discussion post rather than formal docs).
- LiveKit explicitly built its turn-detector because pure VAD "only considers when a user is speaking" — their model additionally considers the semantic content of what has been and is being said to predict true end-of-turn, fine-tuned from Qwen2.5-0.5B-Instruct for this reason, and v1 fuses semantic + acoustic signals directly from audio (not requiring a separate transcript round-trip) across 14 languages — [LiveKit on X launch announcement](https://x.com/livekit/status/1870194686532694417), [LiveKit blog: Solving end-of-turn detection v1.0](https://livekit.com/blog/solving-end-of-turn-detection).
- Smart Turn v2/v3 is explicitly framed by Daily/Pipecat as a "semantic VAD" that detects whether a human has stopped speaking and expects a response, as opposed to plain acoustic VAD; v3 is open source end-to-end (weights, training data, and training code) and licensed BSD-2-Clause, runs on CPU in ~12ms, and supports 23 languages — [X thread by kwindla (Pipecat)](https://x.com/kwindla/status/1966359269080707363), [Daily blog: Announcing Smart Turn v3](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/).
- TEN VAD (a pure acoustic VAD, not a semantic turn detector) reports higher accuracy/lower false-positive rate than WebRTC VAD and Silero VAD on TEN's own "TEN VAD Test Sample" benchmark (one cited comparison: 78.66% accuracy / 64.38% precision / 74.69% recall / 69.15% F1, mean latency 24.20ms) and ~0.17ms average per-frame inference time, with TEN claiming Silero VAD "suffers from a delay of several hundred milliseconds" in some scenarios — [TEN VAD docs](https://theten.ai/docs/ten_vad), [Agora blog on TEN VAD and turn detection](https://www.agora.io/en/blog/making-voice-ai-agents-more-human-with-ten-vad-and-turn-detection/) (TEN's own benchmark; note this measures acoustic VAD quality, not semantic turn-completion accuracy, and is a vendor-reported comparison not independently reproduced here).
- Smart Turn v2 benchmarked latency on real hardware for analyzing 8 seconds of audio: ~12ms (NVIDIA L40S), ~19ms (A100), ~75ms (NVIDIA T4 / AWS g4dn.xlarge), ~410ms (16-core x86_64 CPU, Modal) — [Hugging Face pipecat-ai/smart-turn-v2](https://huggingface.co/pipecat-ai/smart-turn-v2). Smart Turn v3 is reported to bring CPU inference itself down to ~12ms, i.e., comparable to v2's GPU numbers — [Daily blog: Announcing Smart Turn v3](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/).

### Inferences
- The practical pattern across all three semantic-turn systems (Kyutai, LiveKit, Smart Turn) is "VAD/acoustic layer detects a candidate pause → semantic layer classifies whether that pause is a true end-of-turn," and the semantic layer's own compute cost has fallen low enough (Smart Turn v3: ~12ms on CPU) that it's no longer a meaningful latency or hardware tax on top of VAD — the real cost is the extra model (and, for LiveKit's 0.5B Qwen-based detector, nontrivially more parameters than Smart Turn's 94.8M) rather than added latency.
- Given Smart Turn v3's 23-language support (explicitly including German) and BSD-2-Clause license with fully open weights/training data/code, it looks like the most flexible, lowest-footprint, and most permissively licensed semantic turn detector of the three for a bilingual (English+German) local voice agent; LiveKit's turn-detector (14 languages, Qwen2.5-0.5B-based) is heavier but fuses raw-audio + semantic signals directly; Kyutai's semantic VAD is tightly coupled to Kyutai's own STT stack and (per the HF discussion found) not yet available in all serving implementations and only on their smaller model.

### Gaps
- No quantitative false-interruption-rate comparison (e.g., "X% fewer false interruptions than Silero VAD alone") was found for Smart Turn, LiveKit's turn-detector, or Kyutai's semantic VAD; the claims above are qualitative (what each system is designed to avoid) rather than measured reductions.
- No explicit license was found for LiveKit's turn-detector in this pass (only that it is "open-weights" and hosted on Hugging Face); this should be confirmed directly on the model card before relying on it.
- No explicit confirmation was found of German-language support/accuracy specifically for LiveKit's turn-detector or Kyutai's semantic VAD (Smart Turn v3's German support is confirmed via its 23-language list); this is a gap for the English+German requirement.
- WebRTC VAD itself was not independently re-benchmarked in this pass beyond being named as the lower baseline that TEN VAD and Silero VAD are compared against; no primary-source WebRTC VAD accuracy/latency figures were retrieved.

## Additional candidate notes (supporting detail gathered during research)

- **Moonshine** (Useful Sensors): variants from ~27M up to 245M parameters (Tiny ~34M, Small ~123M, Medium ~245M per one source); MIT-licensed; targets mobile/embedded low-latency streaming use. English WER ~7.8% on standard benchmarks per one source, with a newer "2026 streaming line" reportedly reaching 6.66% average WER on the Open ASR Leaderboard (unverified against the leaderboard directly in this pass). A German transfer-learned Moonshine-Tiny model exists with ~11.4% WER on Common Voice — [UsefulSensors/moonshine-tiny](https://huggingface.co/UsefulSensors/moonshine-tiny), [fidoriel/moonshine-tiny-de](https://huggingface.co/fidoriel/moonshine-tiny-de), [UsefulSensors/moonshine-streaming-tiny](https://huggingface.co/UsefulSensors/moonshine-streaming-tiny), aggregator cross-check: [Northflank STT roundup](https://northflank.com/blog/best-open-source-speech-to-text-stt-model-in-2026-benchmarks). Moonshine explicitly ships streaming variants, making it a candidate for genuinely low-resource streaming STT on either target platform.
- **Vosk**: the German server model `vosk-model-de-0.21` is ~1.9GB with WERs ranging 9.83–33.26% depending on test set (telephony/podcast/CommonVoice/MLS/mTEDx); smaller models trade accuracy for a much smaller footprint (e.g., 41MB vs 1.4GB models, with WER roughly doubling for the smaller one) — [alphacep/vosk-space models.md](https://github.com/alphacep/vosk-space/blob/master/models.md). Vosk is a genuinely streaming (partial + final result) API with near-zero added latency, Apache-2.0 licensed, and has first-class German models, making it a reasonable low-footprint fallback if Parakeet/Whisper/Kyutai integration proves impractical, at a meaningfully lower accuracy ceiling than modern transformer/conformer models.
- **sherpa-onnx streaming Zipformer**: part of the actively maintained k2-fsa/sherpa-onnx project (broad platform support: Raspberry Pi, embedded, x86_64, mobile, NPUs), bundling a large zoo of pretrained streaming Zipformer-transducer models; third-party "Kroko" Zipformer2-based streaming models include a German variant (~57MB) — [GitHub k2-fsa/sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx), [k2-fsa Zipformer-transducer model list](https://k2-fsa.github.io/sherpa/onnx/pretrained_models/online-transducer/zipformer-transducer-models.html). No German WER figure was found for these models in this pass (gap).
- **NVIDIA Canary-1B-v2**: multilingual ASR+AST model covering 25 European languages including German; reports German WER of 4.4% on FLEURS, an average WER of ~8.1% across its full 24-language multilingual eval and ~5.2% on a "common-language" subset, beating Whisper large-v3 (9.9%) and SeamlessM4T-medium (12.0%) while trailing SeamlessM4T-v2-large (7.2%) slightly — [arXiv:2509.14128 (Canary-1B-v2 & Parakeet-TDT-0.6B-v3 paper)](https://arxiv.org/pdf/2509.14128), [nvidia/canary-1b-v2 on Hugging Face](https://huggingface.co/nvidia/canary-1b-v2/blob/75a41cc0ecb3f3f8c548119f307b4fc268d50a58/README.md). This makes Canary-1B-v2 the strongest-sourced option in this research for English+German coverage from a single NVIDIA model family, at the cost of being a larger (~1B-parameter), non-streaming model.
- **Parakeet license**: Parakeet-TDT models (v2 and v3) are released under CC-BY-4.0, explicitly permitting commercial use with attribution — [nvidia/parakeet-tdt-0.6b-v2](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v2), [nvidia/parakeet-tdt-0.6b-v3](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3), cross-checked via aggregator [freeapihub Parakeet TDT page](https://freeapihub.com/ai-models/parakeet).
- **distil-whisper German support**: distil-whisper's official English-only line has no built-in multilingual support, but community/vendor German distillations exist — e.g. `sanchit-gandhi/distil-whisper-large-v3-de-kd` (Normalised WER 6.324%, Orthographic WER 8.233%) and `primeline/distil-whisper-large-v3-german` (756M params, 1.51GB in bf16) — [sanchit-gandhi/distil-whisper-large-v3-de-kd](https://huggingface.co/sanchit-gandhi/distil-whisper-large-v3-de-kd), [primeline/distil-whisper-large-v3-german](https://huggingface.co/primeline/distil-whisper-large-v3-german). A multilingual distilled variant covering 7 European languages (incl. German) with 2 decoder layers also exists from a community author — [bofenghuang/whisper-large-v3-distil-multi7-v0.2](https://huggingface.co/bofenghuang/whisper-large-v3-distil-multi7-v0.2).
- **TTS headroom reference numbers** (for the combined-memory question): Kokoro-82M ≈ 2–3GB VRAM (or CPU), Apache-2.0, 54 voices/8 languages; Piper ≈ 0.3GB VRAM/RAM, ~300MB model, ~96x real-time even on CPU, 47 languages/900+ voices — [localaimaster Voice AI VRAM guide](https://localaimaster.com/blog/voice-ai-vram-requirements-by-gpu) (aggregator; primary Kokoro/Piper model cards should be checked to confirm exact VRAM figures before finalizing a deployment budget).

## Overall recommendations (synthesis for the report writer)

These are inferences drawn from the cited findings above, not independently benchmarked by this researcher; treat as a starting recommendation to validate empirically before committing.

**Apple M1, 8GB:** Favor the smallest capable models given shared unified memory. STT: whisper.cpp (Metal or CoreML) with `small`/`medium`, or Moonshine (Tiny/Small, MIT, streaming-capable, tiny footprint) or parakeet-mlx 0.6B (≈2GB minimum per the community repo) for better accuracy than small Whisper at similar footprint. VAD: Silero VAD or TEN VAD (negligible cost either way). Turn detection: Smart Turn v3 (BSD-2-Clause, 23 languages incl. German, ~12ms CPU) is the best-fit semantic turn detector for this constrained, CPU-only-friendly setup. Avoid large-v3/Canary-1B/Kyutai-2.6B class models on 8GB; leave room for TTS (Piper is essentially free; Kokoro is feasible but tight) and any LLM.

**Apple M1, 16GB:** Same stack but room to move up to whisper large-v3-turbo via whisper.cpp/WhisperKit/MLX-Whisper, or Canary-1B-v2/parakeet-mlx larger variants, for better English+German accuracy, while still running Smart Turn v3 + Silero/TEN VAD + Kokoro/Piper TTS comfortably alongside a modest local LLM.

**RTX 3070, 8GB VRAM:** STT: Parakeet-TDT-0.6B (v2 for English-only leaderboard-topping accuracy, or v3/Canary-1B-v2 if German is a hard requirement — Canary-1B-v2's sourced German FLEURS WER of 4.4% is the strongest German number found in this research) via NeMo or an ONNX port (sherpa-onnx/onnx-asr); fall back to faster-whisper large-v3-turbo (int8, ~1.5GB VRAM) if Parakeet/Canary tooling integration is a blocker, using `hotwords` for technical-vocabulary biasing. VAD: Silero or TEN VAD (trivial cost, can run CPU-side). Turn detection: Smart Turn v2/v3 (sub-20ms even on modest GPUs, 12ms on CPU for v3) layered on top of VAD. This leaves roughly 4–6GB of the 8GB VRAM budget free for Kokoro or Piper TTS and for a quantized local LLM if one is also GPU-resident — though the LLM, not the voice stack, is the most likely thing to force hard trade-offs on this card.

**Cross-cutting:** For true incremental streaming transcripts (not just a fast batch pass after VAD), Kyutai STT is the only candidate offering by-design streaming with sub-second fixed delay and a built-in semantic VAD — worth prototyping if the agent needs visible partial transcripts while the user is still talking, but its ecosystem/tooling maturity and per-implementation feature parity (e.g., semantic VAD not yet in all server implementations) should be checked directly before committing, since this was not independently verified against Kyutai's own docs beyond a community discussion thread.
