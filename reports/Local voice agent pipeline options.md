# Phone-call voice managers for coding agents are buildable now

A local-first, phone-call-style "voice manager agent" that orchestrates Claude Code, OpenCode, and T3 Code threads while keeping every speech component (VAD, turn detection, STT, TTS) on-device is technically feasible today, and the realistic latency target is **450-800ms voice-to-voice**, not the ~200ms of human conversation — close enough to feel like a competent phone agent rather than an IVR system. No existing open-source project does exactly this: the closest prior art, **Qwen Audio Agent** and **Paseo**, each solve half the problem (voice-native ACP orchestration, or multi-session agent management with a voice mode bolted on), but nothing treats several live Claude Code/OpenCode/T3 sessions as independently addressable "callers on hold" the way a phone-call manager would. The good news is that the hard infrastructure — VAD, semantic turn detection, STT, TTS, and the streaming/interrupt primitives in the Claude Agent SDK and OpenCode's HTTP server — is mature, actively maintained, and cheap: a usable local voice stack fits in well under 2GB of memory, and the real resource and latency pressure comes from wherever the conversational LLM and the agent harness sit. On an M1 Mac (8-16GB) or an RTX 3070 (8GB VRAM), the voice stack is a rounding error; the hard constraint is squeezing a fast "talker" model alongside it, which argues for either a small local LLM (Qwen3-4B) or routing the fast layer to a cloud model like Claude Haiku while keeping speech fully local. The path forward that actually matches Kyutai Unmute's architecture, confirmed directly from its own repo: Unmute is explicitly LLM-agnostic via an OpenAI-compatible endpoint, which means a Claude Agent SDK or OpenCode-backed shim can sit behind it with no model surgery — but doing so naively collides with the fact that Unmute and comparable cascaded pipelines are tuned for sub-second turns, not the multi-second, tool-calling turns an agent harness actually takes, so the dual-model "talker-reasoner" split is the architecture to build around regardless of which framework carries the audio.

## Nobody has built the exact thing, but three adjacent projects show the shape of it

No OSS project today is purpose-built as "a voice manager that orchestrates multiple coding-agent sessions by phone call." That specific shape is genuinely greenfield, confirmed by a systematic survey of ~25 Claude-Code/OpenCode voice wrappers, the ACP ecosystem, and the major multi-agent dashboards. The closest analog is **Qwen Audio Agent** (`QwenAudio/qwen-audio-agent`, ~3,100 stars, Apache-2.0, pushed 2026-10-29), a realtime voice runtime explicitly built on ACP that separates a lightweight conversational "Frontend Agent" from an "Orchestration Runtime" handling task admission, queueing, and permission routing, from a "Backend Agent" doing the actual coding work via native ACP (OpenCode, Qoder, Kimi) or external ACP adapters (Codex, **Claude Code**) ([GitHub QwenAudio/qwen-audio-agent](https://github.com/QwenAudio/qwen-audio-agent)). Its `spawn_thinking(objective)` primitive never blocks the voice layer on backend work, it enforces one active task slot globally and one per owner with later requests queued, and it resolves backend permission prompts through natural-language yes/no voice responses — all directly reusable design patterns for a true multi-session manager, even though Qwen Audio Agent itself still centers on one voice conversation driving one coordinator session per backend rather than a dashboard of N independent sessions ([Qwen Audio Agent architecture deep-dive](https://github.com/QwenAudio/qwen-audio-agent)). **Paseo** (`getpaseo/paseo`, ~22,400 stars, Apache-2.0) is the closest match on the "orchestrate many coding-agent sessions across providers" half of the brief — true multi-session, multi-provider, worktree-based orchestration across Claude Code, Codex, OpenCode, and more — and it ships a real local-first Voice Mode (ONNX Parakeet-tdt-0.6b for STT, Kokoro for TTS, cloud OpenAI fallback) that drives "a hidden agent session using your configured provider" via an MCP stdio bridge ([Paseo voice.md](https://github.com/getpaseo/paseo)). But Paseo's voice mode is one voice-accessible orchestrator session, not an outer loop that owns and narrates across many independently addressable sessions. A long tail of single-maintainer MCP voice servers (`mbailey/voicemode` at ~1,428 stars being the most mature) wrap a single existing Claude Code session with push-to-talk STT/TTS, useful as plumbing references (local Whisper.cpp + Kokoro patterns) but architecturally the wrong layer — they're tools the coding agent calls, not a process that drives multiple agents. Both the Claude Agent SDK and OpenCode's HTTP server already expose everything a manager needs — streaming message generators, `interrupt()`/`abortController` or `/session/:id/abort`, and full session list/resume/fork APIs — so the genuinely open engineering problem is the orchestration layer that juggles multiple live sessions as voice-addressable peers, decides when it's safe to interject a status update, and maps ambiguous references ("tell the OpenCode one to stop") onto the right session handle. No public design exists for that cross-session barge-in/priority problem; it is the hard, unsolved part of this project.

## Feels human is off the table, but 450-800ms is a solid target

Human conversational turn-taking averages a ~208ms gap across ten languages, a widely cited empirical benchmark ([dev.to summary of Stivers et al. via ACL IWSDS 2025](https://dev.to/kenimo49/200ms-humans-vs-700ms-voice-agents-what-acl-iwsds-2025-says-about-the-turn-taking-gap-2iap)), and no LLM-in-the-loop architecture — agent harness or not — gets close to that. Industry consensus instead treats **sub-500ms as "feels human," 300-600ms as sluggish-but-acceptable, and >600-800ms as where callers mentally revert to IVR expectations** ([Forasoft LiveKit AI Voice Agents Playbook](https://www.forasoft.com/blog/article/livekit-ai-agents-guide)). A representative p50 budget split is endpointing/VAD ~80ms + ASR finalization ~120ms + LLM time-to-first-token ~180ms + TTS time-to-first-audio ~70ms, landing around 450ms total before network overhead ([Evalgent, LiveKit vs Pipecat Latency](https://www.evalgent.com/blog/livekit-vs-pipecat-latency)); Kyutai's production Unmute deployment reports conversational latency typically **400-750ms** with a semantic VAD that avoids interrupting mid-sentence pauses ([Kyutai Unmute docs](https://www.mintlify.com/kyutai-labs/unmute/introduction)). The real bottleneck for this project is not the voice stack — it's the agent harness. Headless `claude -p` invocations pay process-startup/discovery overhead on top of the underlying API call: one tracked regression shows median time-to-first-stdout climbing from 1,553ms to 2,295ms across recent versions ([GitHub anthropics/claude-code#87652](https://github.com/anthropics/claude-code/issues/87652)), and both the Claude Agent SDK's partial-message streaming and OpenCode's SSE event stream have open, currently-unresolved bugs around buffering and dropped events ([GitHub anthropics/claude-agent-sdk-typescript#511](https://github.com/anthropics/claude-agent-sdk-typescript/issues/511); [GitHub anomalyco/opencode#26866](https://github.com/anomalyco/opencode/issues/26866)). ACP formalizes streaming (`session/update`) and cancellation (`session/cancel`) but explicitly disclaims any latency guarantee — it only standardizes ordering and semantics, not speed ([agentclientprotocol.com, Prompt Lifecycle](https://agentclientprotocol.com/protocol/v2/prompt-lifecycle)). The proven way to reconcile a multi-second, tool-calling agent harness with a sub-800ms voice loop is the **talker-reasoner dual-model split**: a fast conversational model owns the microphone and every turn, while the slow harness runs as an async background worker whose first progress update releases the conversation so the fast model can say "still looking into it" and keep talking ([LiveKit, The talker-reasoner pattern for voice agents](https://livekit.com/blog/talker-reasoner-pattern-voice-agents)). This mirrors OpenAI Realtime's native `async: true` tool primitive and Pipecat's `cancel_on_interruption=False` async function-call pattern, both built for exactly this "don't let a slow tool call create dead air" problem ([OpenAI, Async tool calling guide](https://developers.openai.com/api/docs/guides/async-tool-calling); [Pipecat docs, Function Calling](https://docs.pipecat.ai/pipecat/learn/function-calling)). Separately, a wired or low-latency Bluetooth headset is the pragmatic recommendation over laptop speaker+mic: WebRTC AEC3 and macOS's native VoiceProcessingIO both reliably struggle with "double-talk" — false-suppressing the user's interrupting speech exactly during barge-in, the one moment this project depends on working well ([coval.ai, Voice AI Echo Cancellation](https://www.coval.ai/blog/voice-ai-echo-cancellation/)).

## The local voice stack is settled, cheap, and in some cases German-capable

Across VAD, turn detection, STT, and TTS, there is now a clear, actively-maintained best choice for each layer, and together they consume a small fraction of an 8GB budget. For **VAD**, Silero VAD (309K parameters, ~1-2MB, <1ms per chunk, MIT) or TEN VAD (claimed ~48% faster, Apache-2.0) are both negligible-cost, CPU-only, and language-agnostic ([GitHub snakers4/silero-vad](https://github.com/snakers4/silero-vad); [TEN VAD docs](https://theten.ai/docs/ten_vad)). For **semantic turn detection** — the layer that actually prevents the agent from barging in during a mid-sentence pause — **Smart Turn v3** (Pipecat/Daily) is the standout: ~8M parameters, 8MB int8, **12ms CPU inference**, 23 languages including German at 96.1% accuracy, fully open weights/training data/code under BSD-2-Clause ([Daily blog, Announcing Smart Turn v3](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/)). LiveKit's turn-detector (Qwen2.5-0.5B-based, 14 languages including German) is a credible alternative but is heavier (~400MB) and its weights sit under a separate, non-fully-open LiveKit Model License ([docs.livekit.io, turn-detector](https://docs.livekit.io/agents/logic/turns/turn-detector/)). For **STT**, the choice splits by platform: on the RTX 3070, **NVIDIA Parakeet-TDT-0.6B** tops the Open ASR Leaderboard at 6.05% WER with an RTFx of 3,380 in batch, and v3 adds 25-language multilingual support (German WER 5.04% on FLEURS) under CC-BY-4.0 ([HF nvidia/parakeet-tdt-0.6b-v2](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v2); [HF nvidia/parakeet-tdt-0.6b-v3](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3)); faster-whisper (large-v3 int8, ~2.9-3.1GB VRAM) is the fallback if Parakeet tooling integration is a blocker, with a documented `hotwords` parameter for biasing toward repo names and CLI commands ([theneuralbase, hotwords docs](https://theneuralbase.com/faster-whisper/learn/intermediate/hotwords-parameter-v1-0/)). On the M1, **WhisperKit** (CoreML/ANE, ~0.45s mean per-word latency) or **parakeet-mlx** (community MLX port, ~2GB minimum unified memory) are the strongest low-latency options, with whisper.cpp's Metal/CoreML path as the mature fallback ([Argmax WhisperKit benchmarks](https://github.com/argmaxinc/argmax-oss-swift/discussions/243); [GitHub senstella/parakeet-mlx](https://github.com/senstella/parakeet-mlx)). For **TTS**, **Kokoro-82M** (Apache-2.0, ~2-3GB VRAM, TTS Arena-leading naturalness, German via community fine-tunes) and **Piper** (GPL-3.0 now via the OHF-Voice/piper1-gpl successor to the archived original, ~0.3GB, 96x real-time on CPU alone) are the two most framework-mature choices, both with first-class Pipecat support ([LiveKit blog, best open source frameworks](https://livekit.com/blog/best-open-source-voice-and-video-ai-agent-frameworks)); **Kyutai Pocket-TTS** (MIT, native German support including a 24-layer German variant) is worth prototyping for the bilingual case, though no streaming time-to-first-audio benchmark was found for it specifically ([kyutai-labs/pocket-tts](https://github.com/kyutai-labs/pocket-tts)). On the orchestration-framework layer, **Pipecat** (~16.9k stars, BSD-2-Clause, maintained by Daily, weekly release cadence) is the best overall fit: its `FrameProcessor`/`Pipeline` abstraction treats the LLM as just one swappable processor rather than an OpenAI-shaped plugin slot, it ships first-party local STT/TTS services, and `LocalSmartTurnAnalyzerV3` ships bundled with the core package, no separate download ([docs.pipecat.ai, Smart Turn overview](https://docs.pipecat.ai/api-reference/server/utilities/turn-detection/smart-turn-overview)). **LiveKit Agents** (~15k stars, Apache-2.0) is the strongest runner-up, with more polished async-tool and filler-speech primitives (`session.say()`, `ctx.foreground()`, a configurable background-tool-status template) but requires self-hosting a separate media-server process and leans more on cloud STT/TTS providers than Pipecat's in-process local services ([LiveKit blog, Async tools for voice agents](https://livekit.com/blog/async-tools-voice-agents)). Among full-duplex speech-to-speech models, only **Kyutai Unmute** cleanly fits a bring-your-own-harness requirement: it is explicitly architected as local STT/TTS wrapped around *any* text LLM reached via an OpenAI-compatible endpoint (`KYUTAI_LLM_URL`), with tool-calling deliberately left for the LLM server to implement invisibly — meaning a Claude Agent SDK or OpenCode shim behind that endpoint plugs in with no model surgery, confirmed directly from Unmute's own README ([GitHub kyutai-labs/unmute](https://github.com/kyutai-labs/unmute)). Every other speech-to-speech model surveyed (Moshi, Qwen-Omni, Ultravox, Sesame CSM) fuses reasoning into the audio model itself and cannot cleanly host an external agent harness without model surgery.

## Hardware reality: the voice stack is a rounding error, the LLM is the constraint

On both target platforms, VAD and turn detection together cost well under 500MB of memory and are effectively free relative to any budget. The real sizing question is STT + TTS + whatever LLM sits alongside them. On the **RTX 3070 (8GB VRAM)**, a Parakeet-TDT-0.6B STT (~1-2GB) plus Smart Turn v3/Silero VAD (sub-20MB) plus Kokoro or Piper TTS (0.3-3GB) sums to roughly 2-5GB, leaving 3-6GB free — comfortably enough for a quantized 3-4B local LLM but tight for a 7-8B model, since Whisper large-v2/v3 at fp16 alone already consumes 4.5GB and aggregator guidance puts a comfortable full STT+LLM+TTS stack closer to a 24GB card ([localaimaster, VRAM by GPU](https://localaimaster.com/blog/voice-ai-vram-requirements-by-gpu)). Qwen3-8B at Q4 fits in ~5-6.5GB on the 3070, which leaves only 1.5-3GB for STT+TTS — workable but with little headroom for context length; Qwen3-4B (~2.5-3GB) is the safer choice when the LLM must be local and GPU-resident alongside the voice stack ([modelfit.io, RTX 3070 8GB for Local LLMs](https://modelfit.io/gpu/rtx-3070/)). On the **M1 Mac**, unified memory removes the hard VRAM wall but means the voice stack competes directly with the OS and any LLM for the same pool: at **8GB**, favor the smallest capable models throughout — whisper.cpp small/medium or Moonshine for STT, Smart Turn v3 for turn detection, Piper (near-free) or a tight Kokoro build for TTS — and treat a resident conversational LLM as a real constraint, not an afterthought. At **16GB**, there is comfortable headroom to run Qwen3-8B at Q4 (~18 tok/s per community Ollama benchmarks) alongside the full voice stack ([codersera.com, Run Qwen3-8B on Mac](https://codersera.com/blog/run-qwen-3-8b-on-mac-an-installation-guide/)). No source in this research measured a genuine combined STT+VAD+turn+TTS+LLM deployment on either target — all figures above are summed from independently-benchmarked components, so real-world contention (CUDA context overhead, concurrent model-loading, OS memory pressure) could eat into the stated headroom; validating this empirically before committing to a specific hardware configuration is warranted. The practical conclusion either way: a fast cloud model (Claude Haiku, ~600ms TTFT with no caching, far better with prompt-cache pre-warming) sidesteps this memory contention entirely at the cost of network RTT, making "local LLM vs. cloud-routed-through-the-harness" a genuine either/or decision rather than a given.

## Three candidate architectures to choose between

**Architecture A — Pipecat + talker-reasoner split, fast layer local.** Pipecat (SmallWebRTC transport, Silero VAD, Smart Turn v3, Parakeet-TDT or Whisper STT, Kokoro/Piper TTS) runs a small local LLM (Qwen3-4B) as the always-on "Talker," which owns every turn and dispatches to the Claude Agent SDK / OpenCode server / ACP session as a single async tool call per the talker-reasoner pattern. *Trade-off:* fully local and private end-to-end except the one agentic hop; lowest network dependency; but the 4B talker's conversational and intent-parsing quality is noticeably weaker than a frontier model, and on an 8GB RTX 3070 or 8GB M1 this is the tightest memory fit of the three.

**Architecture B — Pipecat + talker-reasoner split, fast layer cloud (Claude Haiku).** Same voice stack and pipeline, but the fast conversational layer is Claude Haiku via the direct API (not through the harness), reserving the slow agent-harness hop for actual delegation. *Trade-off:* removes the local-LLM memory contention entirely and gives much better conversational quality/instruction-following for routing decisions; costs network RTT on every turn (Haiku TTFT ~600ms uncached, much lower with prompt-cache pre-warming) and makes "speech-related must run locally" technically true (voice stack is 100% local) while two separate LLM calls now leave the device — acceptable per the brief's own carve-out that only the LLM step may be external, but worth being explicit that this is now two external LLM calls (talker + reasoner), not one.

**Architecture C — Build directly on Kyutai Unmute, harness behind an OpenAI-compatible shim.** Point Unmute's `KYUTAI_LLM_URL` at a thin adapter process that forwards transcripts to the Claude Agent SDK, OpenCode's `/session` API, or an ACP session, and streams back text for Unmute's TTS. *Trade-off:* least custom orchestration code to write, since Unmute already owns VAD/STT/TTS/turn-taking end-to-end and the integration point is a documented, stable HTTP contract — but Unmute's turn-taking and barge-in logic is tuned for sub-second LLM turns, and no source confirms its behavior under the multi-second, multi-tool-call latency of a real agent-harness turn; this would need the talker-reasoner split layered on top anyway (the adapter itself would need to return a fast acknowledgment and defer the real harness result), making this closer to "Architecture A/B implemented with Unmute's plumbing" than a genuinely simpler path. Unmute also requires a CUDA GPU with ≥16GB VRAM for its own default stack (STT 2.5GB + TTS 5.3GB + a default local LLM), which doesn't fit the RTX 3070's 8GB without swapping components — making it a better fit for a separate, more capable GPU than the two target machines in this brief, or for running the STT/TTS halves only against a lighter local LLM.

## What this changes about how to think about the project

The research reframes the problem from "can local speech + remote agent latency work at all" (yes, comfortably, within the 450-800ms band production systems already ship at) to "how do you make a multi-second agentic tool call feel conversational," which is squarely a UX and orchestration problem, not a speech-infrastructure problem — every piece of the local voice stack (VAD, turn detection, STT, TTS) is solved, cheap, and interchangeable, while the talker-reasoner split, async tool calling, and cross-session barge-in scheduling are the actual unsolved engineering surface. The most consequential open question the sources could not answer is what happens when *multiple* backend agent sessions want to announce completion while the user is mid-conversation with a third one — no project surveyed, including Qwen Audio Agent's otherwise-sophisticated admission-queue design, has published a policy for that, and it is precisely the scenario a "manage my fleet of coding agents by phone call" product cannot avoid. Building Architecture A or B first, with a single backend session, and only then generalizing the async-tool-call pattern to N concurrent sessions, is the lowest-risk way to discover that scheduling policy empirically rather than designing it blind.
