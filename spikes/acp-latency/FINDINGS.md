# Findings: harness over ACP as the voice "talker"

Spike date 2026-10-29. claude-agent-acp 0.99.0 (bundled Claude Code from claude-agent-sdk 0.3.312),
`claude` CLI 2.1.280 login (subscription OAuth, no API key), opencode 1.18.31, `@agentclientprotocol/sdk`
2.1.0, Bun 1.4.2. One long-lived session per run: 8 short voice turns, a barge-in and a follow-up.
2–3 runs per config, so 14–21 warm turns per config. All times are ms after `session/prompt` was sent.
Treat these as indicative, not statistically solid.

## TL;DR

- **No config reliably hits "first speakable sentence ≤ 1 s".** The best warm medians are a
  **TTFT of about 1.25–1.45 s** and a **first sentence of about 1.4–1.8 s**, with p90 at 2–3.5 s.
  For Claude, the first sign of life is a `usage_update` (the API's message start) at about
  1.2–1.4 s. Shrinking the Claude Code system prompt did not move that floor, so it looks like
  API/route time to first byte, not harness overhead.
- **Each tool hop costs about 1.2–1.5 s** (another model call after the MCP result). With
  `dispatch_task` or `list_sessions`, a turn ends at about 3 s. The MCP plumbing itself is cheap:
  under 10 ms when tools are pre-allowed, about 150 ms with an ACP permission round trip.
- **Barge-in is excellent.** `session/cancel` resolves the prompt with `stopReason: cancelled`
  in 2–9 ms on Claude and about 45 ms on OpenCode. At most 3 chunks arrive after the cancel. The
  next turn in the same session works normally and keeps its context.
- **Biggest knob: `ENABLE_TOOL_SEARCH=false`.** By default Claude Code defers MCP tools behind
  `ToolSearch`, which adds a whole extra model round trip (about 1.4 s) the first time each tool
  is used in a session. Second knob: pre-allow the MCP tools (`allowedTools`), which saves about
  150 ms per call. Replacing the system prompt, removing built-in tools and disabling thinking gave
  no measurable TTFT gain on Haiku; prompt caching seems to make the big preset cheap.
- **Verdict:** usable as the talker only with a local instant acknowledgement and filler, and with
  the expectation that real content starts about 1.5–2 s after end of speech (plus STT/TTS time).
  That is a competent-but-slow phone agent, not a snappy one. Recommended config:
  claude-agent-acp + Haiku 5.5, default prompt + persona append, tool search off, MCP tools
  pre-allowed, plus a warm-up turn. Details below.

## Per-configuration tables

Generated by `bun analyze.ts` (also in `results/tables.md`; raw data in `results/*.json`,
condensed in `results/summary.json`). Definitions:

- *first update*: any `session/update`. For Claude this is always `usage_update`, which arrives
  about 200 ms before text. For OpenCode it is usually `agent_thought_chunk`, because deepseek
  streams its reasoning.
- *first content*: the first message chunk, thought chunk or `tool_call`.
- *first sentence*: the chunk at which the accumulated text first contains `[.!?]` followed by
  whitespace or end of buffer.
- *Tool rows*: ACP `tool_call` → MCP server log → ACP `tool_call_update completed` → next text chunk.
  Negative values mean opencode announces a tool call after it has already run.

## Barge-in / cancel

All configs behaved well. Across 17 barge-ins:

- **cancel → prompt resolves**: 2–9 ms on claude-agent-acp, 43–47 ms on OpenCode, always with
  `stopReason: "cancelled"` once the prompt was running.
- **Output after cancel**: 0 chunks in most runs, at most 3 chunks within 12 ms (already in flight).
  Nothing arrived later in the 1.5 s observation window.
- **The next turn in the same session is normal**: TTFT 0.5–2.4 s (one 5.6 s outlier on OpenCode), context intact (it answered
  "which agent needs my input" correctly from earlier tool results).
- Sonnet-b and one opencode-b run produced no text within 5 s for the "explain in detail" prompt,
  so the cancel came from the timer before any output. That is a TTFT outlier, not a cancel problem.
- One quirk: when OpenCode hangs on a provider error (see below), `session/cancel` makes the
  prompt return **`end_turn`** rather than `cancelled`.

## Adapter knobs

### claude-agent-acp 0.99.0

| knob | how | effect observed |
|---|---|---|
| Model | `_meta.claudeCode.options.model` on `session/new` (alias or id). It can also be changed later with `session/set_config_option` `configId:"model"`. Options offered: default, opus (5.5), fable (5.1), sonnet (5.5), haiku (5.5), Haiku 4.5, Sonnet 5, Opus 5, … | Haiku 5.5 and Sonnet 5.5 have similar TTFT here (Sonnet even had a lower no-tool median in variant a). Sonnet streams about 4× slower (≈150 vs ≈600–700 chars/s) and has much worse p90/tool-resume tails. Haiku is the better talker. |
| System prompt | The ACP spec field `systemPrompt: {mode: "append"\|"override", content}` (advertised in `sessionCapabilities.systemPrompt`). Alternatively `_meta.systemPrompt`: a string replaces the prompt; an object is merged into the `claude_code` preset (`append`, `excludeDynamicSections`, `snapshot`). | Replacing the large preset with the about 800-char persona gave **no measurable TTFT gain** (no-tool TTFT 1331 vs 1263–1428). Caching seems to neutralise the size. Persona compliance was similar either way. |
| Built-in tools | `_meta.claudeCode.options.tools: []` (or a list), `disallowedTools`, legacy `_meta.disableBuiltInTools` | No latency effect seen. Useful for safety and to keep the talker from wandering. |
| MCP tool deferral | `_meta.claudeCode.options.env.ENABLE_TOOL_SEARCH = "false"` | **Big effect on tool turns.** By default the first use of each MCP tool goes `ToolSearch` → MCP tool, costing an extra model call (≈1.4 s; 6 of 6 first uses in the haiku-a runs). Turning it off removes that. |
| Tool permissions | `_meta.claudeCode.options.allowedTools: ["mcp__voice__…"]`, or mode `bypassPermissions` | Without it, every MCP call triggers `session/request_permission`. That costs a median ~150 ms announce→invoke versus ~8 ms when pre-allowed, and the client **must** answer it or the turn stalls. |
| Thinking / effort | `options.thinking: {type:"disabled"}`, `options.effort`, env `MAX_THINKING_TOKENS` | No thought chunks were streamed in any Claude config, and disabling thinking made no visible difference. |
| Settings isolation | `options.settingSources: []` ignores `~/.claude` settings, CLAUDE.md, skills and plugins | Not separately measured; part of variant b. |
| Prompt suggestions | Adapter default `promptSuggestions: true` (predicts a follow-up after every turn); turn off with `false` | No turn-latency effect seen. Turn it off to save tokens. |
| Caching | No ACP-level knob; Claude Code caches automatically. `excludeDynamicSections` makes the preset cacheable across sessions/cwds | The cache-cold first turn costs about 0.5–1 s extra (turn 0 TTFT 1.4–2.6 s vs warm ~1.3–1.4 s). Mitigation: a hidden warm-up prompt at connect time. |
| Anything else | Every other Claude Agent SDK `Options` key passes through `_meta.claudeCode.options` (hooks, env, extraArgs, settings, mcpServers). `initialize` also advertises `_meta.steering.supported` / `promptQueueing`, meaning prompts can be sent while a turn runs. | Steering was not tested. It is interesting for "user keeps talking". |

Auth: the adapter used the existing CLI login (`~/.claude/.credentials.json`) with no API key and
no `authenticate` call needed. `authMethods` was `[]`.

| Tools | Agent `tools: {x: false}` or `permission: {edit/bash/webfetch: "deny"}` | **Disabling tools on the free `opencode/*` models makes every request fail** with "Free usage limit reached" (bisected: `prompt` alone works; `tools:false` alone fails). Built-ins were therefore only permission-denied. |
| MCP | `mcpServers` in `session/new` works. Tools appear as `voice_list_sessions`. | No permission prompt; ~1–20 ms invoke. |

Model choice for OpenCode: no Claude model was reachable. `opencode-go/claude-haiku-5-5` failed
with an expired API key. All `omniroute/*` routes (Claude Haiku/Sonnet, gemini-flash,
deepseek-flash, `auto/fast`) produced no response within 30–60 s; the endpoint itself answers 401 to
a plain curl. I used **`opencode/deepseek-v4.1-flash-free`** (the fastest working free model in a
`opencode run` probe), so OpenCode numbers measure a **different model** and are not an
apples-to-apples harness comparison. That model streams reasoning as `agent_thought_chunk` before
text.

## Surprises, bugs, failure modes

1. **MCP tool deferral (`ToolSearch`)** in Claude Code adds a hidden extra LLM round trip on first
   use of each MCP tool. The talker even narrated it once ("I need to load the dispatch tool
   first"). Set `ENABLE_TOOL_SEARCH=false` for a voice talker with a handful of tools.
2. **Default MCP permission prompts**: the adapter asks the client for permission on every MCP call
   unless the tools are pre-allowed. A voice client that doesn't answer stalls the turn.
3. **The talker doesn't always "say something before the tool"**: Haiku skipped the pre-tool
   sentence in about 1/3 of tool calls (haiku-a 9/13, haiku-a-nts 8/14, haiku-b 11/17). That
   leaves 2.5–3.5 s of dead air. Sonnet and deepseek complied every time. **Don't rely on the
   prompt; synthesise a filler client-side on `tool_call` when no text preceded it.**
4. **Text segments around a tool call are concatenated without a separator** ("On it.Done, I've
   sent…"). A TTS sentence splitter must treat `tool_call` as a hard boundary, or "it.Done" is
   not seen as a sentence break.
5. **Streaming is real, not end-of-message buffering.** For Haiku, inter-chunk gaps are p50 ~0–14 ms
   at about 600–700 chars/s. Short replies arrive in 1–2 bursts because the model is simply done
   that fast. Sonnet chunks arrive grouped at about 150 chars/s. Both are far faster than TTS
   playback (~15 chars/s), so after the first sentence, generation is never the bottleneck.
6. **`usage_update` arrives about 150–300 ms before the first text chunk** on Claude. It is a
   free "model is responding" signal, usable for UI or for timing a backchannel.
7. **The first turn of a session is about 0.5–1 s slower** (cache write). Send a warm-up turn.
8. **OpenCode hangs on provider errors**: on a free-tier rate limit or quota error it logs
   `stream error` and keeps retrying, and `session/prompt` never resolves. I added a 45 s
   timeout + cancel to the harness. OpenCode also fires a parallel title-generation LLM request
   with the first prompt.
9. **The OpenCode free tier rejects agents with tools disabled** (see knobs). The free quota is
   also shared across all `opencode/*-free` models and ran out mid-spike; three runs are in
   `results/failed/`.
10. **OpenCode cold start** is 1.7 s, sometimes 5.9 s (the user's model-discovery plugin
    appears to dominate it). claude-agent-acp needs ~0.6 s from spawn to session ready (init 0.27 s,
    `session/new` 0.33 s); the MCP server reports ready about 50 ms after `session/new` returns.
11. **Bun:** no incompatibilities. The harness, `@agentclientprotocol/sdk` client and MCP server run
    on Bun. The adapter runs on node per its shebang, but also ran fine under Bun in one check
    (`ADAPTER_RUNTIME=bun`, cold ready 518 ms vs ~590 ms; result in `results/bun-adapter/`).
    The ACP SDK 2.x API is `client().onNotification/onRequest(...).connect(ndJsonStream(...))`;
    `ClientSideConnection` is gone.
12. Variance is substantial. Sonnet-b had a 6.6 s TTFT and 7.6 s tool resumes in one run with no
    config change, so tails matter more than medians for voice.

## Verdict

**Is "harness over ACP as the talker" viable?** Conditionally. ACP itself is not the problem:
transport, MCP dispatch and cancel overheads are milliseconds. The limit is the model call made
through Claude Code. Its warm floor is about 1.2–1.4 s to first byte and about 1.4–1.8 s to the
first speakable sentence (median), with p90 near 3 s and every tool hop adding another 1.2–1.5 s.
Add local endpointing, STT and TTS time-to-first-audio (≈0.3–0.5 s), and real content lands about
**2–2.3 s after the user stops talking (median), 3.5 s+ at p90**. That misses the ~1 s target and
the 450–800 ms "feels human" band from the prior research. It is tolerable for a "manager on the
phone" only if dead air is covered.

**Use this config if you go this way:** claude-agent-acp + `haiku` (Haiku 5.5), persona via
`systemPrompt` append (or override; it made no latency difference), and
`_meta.claudeCode.options` set to `{ model: "haiku", env: { ENABLE_TOOL_SEARCH: "false" },
allowedTools: ["mcp__voice__*" tools], tools: [], promptSuggestions: false, settingSources: [] }`.
Use Sonnet only if quality demands it; its tails are worse.

**Required mitigations:**
1. **An instant local acknowledgement / backchannel** on end-of-utterance ("mm-hm", "okay"),
   played while the harness thinks. This is mandatory, since nothing from the harness arrives
   within 1 s.
2. **Client-side filler on `tool_call`** when no text preceded it ("one sec, checking"), and a
   hard TTS sentence boundary at every tool call.
3. **A warm-up turn** right after `session/new` to pay the cache-cold first-turn penalty off-line.
   Keep the session long-lived (no `claude -p` per turn).
4. **Barge-in via `session/cancel`** works as-is. Stop TTS locally at once; the agent stops
   within ~10 ms.
5. **Keep tools fire-and-forget and few.** Every tool call is a second model call (~1.3 s), so
   design the MCP tools so one call answers the question (e.g. a `list_sessions` that already
   includes what a status question needs).
6. **Watch provider failure modes:** wrap every prompt in a timeout + cancel (OpenCode can hang
   forever).

**Next measurement worth doing:** raw streaming Haiku TTFT with an API key, using the same persona
and tools. If it is about 0.5–0.6 s, as the prior research suggests, then Claude Code plus the
subscription route costs about 0.7 s per turn. In that case the talker–reasoner split (a direct-API
or local fast talker owning the conversation, with the ACP harness as the async reasoner/dispatcher)
is clearly the better architecture. If raw TTFT is also about 1.2 s, the harness is nearly free and
using it as the talker is fine, given the mitigations above.
